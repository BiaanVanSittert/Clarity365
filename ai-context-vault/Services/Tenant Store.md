# Tenant Store

`src/lib/services/tenant-store.ts` :  **the central hub of the entire application.** ~1700 lines, ~30 public methods.

Every one of the 33 [[API Surface|API routes]] (except the fleet-operations ones, see below) reads or writes through this one file. It is the sole owner of persistence.

## Persistence
- Backed by **SQLite** (`better-sqlite3`, `data/clarity365.db`) :  new as of the auth-system rewrite, see [[Security & Auth]]
- **Auto-migrates** from the legacy flat file `data/clarity-store.json` on first run :  this is why a pre-upgrade install has that JSON file sitting in `data/` (gitignored local state)
- Owns operator auth config (delegates hashing to [[Security Infra]]'s `crypto.ts`) and encrypted tenant client secrets

## What it imports
`fleet-analyzer` ([[Analysis & Generation]]), `mock-tenants`/`default-snapshot`/`baseline-definitions` ([[Baseline Definitions & Mock Data]]), `crypto` ([[Security Infra]]), `graph-client` (4 functions) and `graph-fetch`/`exo-client` (7 functions) ([[Core Graph Layer]]), `mdo-mapper` ([[Data Mappers]]).

## What imports it
Every `src/app/api/**/route.ts` file, plus [[Fleet Operations]] and `scheduler.ts` ([[Security Infra]]).

## Representative methods
`getSnapshot`, `syncTenant` (live Graph pull, falls back to cache), `deployBaselinePolicy`, `addTablEntry`/`removeTablEntry`, `applyMdoBaselineFix`, `disableForwardingRule`, `revokeMailboxDelegation`, `containUserAccount`/`restoreUserAccount`, `isolateEndpointDevice`, `getAuditLog`, `getSettings`/`updateSettings`, `saveSnapshot`.

`getSnapshot`'s private `backfillSnapshot()` runs on every read, deserializing the stored row against `createBlankSnapshot()`'s defaults so no consumer needs to defend against a missing field. For `snapshot.tenant.isDemo` tenants specifically, a handful of fields (`accountClassification.users`, `mailboxes`, `intune.devices`, `incidents`, `signIns`) deliberately prefer whatever's *currently* in `mock-tenants.ts` over whatever's frozen in the database - since a mock tenant never re-syncs (`fetchLiveTenantSnapshot` short-circuits unchanged for `authMode === "mock"`), without this a demo tenant seeded before a mock-data edit would keep serving stale data forever. `signIns` was missing from this list until [[Sign-In Logs & CA Diagnostics]]'s country-code normalization work surfaced it - worth checking this same list first before assuming a `mock-tenants.ts` edit "isn't working" for any other field.

Also fixed: `syncTenant()`'s fully-failed path (Graph token acquisition fails entirely - bad/expired/revoked credentials) previously never updated `Tenant.connectionStatus`, so a tenant that was last "healthy" kept showing "healthy" everywhere indefinitely even while every subsequent sync attempt kept failing - the only trace was a toast at the moment of a manual sync. It now persists a new `"error"` status onto the raw tenant row (same `getTenantRow`/`putTenantRow` patch pattern as `persistExoRefreshToken()`) and reflects it in the stale-fallback snapshot returned to the caller, so a broken live tenant reads as broken everywhere, durably, not just in a dismissable toast.

A second, deeper instance of the same class of bug: `syncTenant()`'s **success** path only ever called `putSnapshotRow()` - persisting the freshly-computed `connectionStatus`/`lastSyncTimestamp` inside the *snapshot's* embedded tenant copy - and never `putTenantRow()`. `getAllTenants()`/`getTenant()` (what the Header badge, the tenant switcher, and `computeFleetPosture()`'s tenant list all actually read) only ever read the raw `tenants` table row, which was therefore frozen at whatever `connectionStatus` it had at creation forever, no matter how many times the tenant synced successfully afterward. Now `syncTenant()`'s success branch also calls `putTenantRow(snapshot.tenant)` (the already-re-encrypted tenant object) so the canonical row and the snapshot's embedded copy never diverge.

`syncTenant()` also writes step-by-step progress (`"Fetching Conditional Access policies..."`, current step index, total steps) into an in-memory, never-persisted `Map` keyed by tenant id (`getSyncProgress()`, exported alongside the class) as `fetchLiveTenantSnapshot` moves through each of its ~17 named fetch steps - polled by `GET /api/tenants/[id]/sync-progress` (same interval-polling pattern `PermissionsModal.tsx` already uses for the EXO device-code flow) so the UI can show a live percentage instead of just a spinner for however long a sync takes. The map entry is always deleted in a `finally`, so a stale "in progress" state can't outlive the sync that created it.

**Dev-server restart friction, fixed:** this file's exported `tenantStore` singleton used to cache the **entire class instance** on `globalThis` in dev mode (to avoid a hot-reload opening a second SQLite connection or duplicating the scheduler's timer) - but that had a real side effect nobody intended: when Next.js recompiled this file after an edit, the cached-instance check still found the *old* instance and reused it, so every method on it kept running pre-edit code until a full process restart, no matter how many times the module itself recompiled. Hit twice in one session (the `backfillSnapshot()` `signIns` fix and a `subscribedSkus` `$top` fix each silently had no effect until a restart). Fixed by splitting what actually needs to survive a hot-reload from what doesn't: only the raw `Database` connection is now cached on `globalThis` (a new, separate cache, `clarity365TenantStoreDb`, checked inside the constructor), while `export const tenantStore = new TenantStore();` always constructs a fresh instance - so its methods are always the latest code on the next request, while still reusing the same open SQLite connection (no duplicate handles, no re-triggered migrations beyond their own already-idempotent no-op checks). The background scheduler (`scheduler.ts`, started once at server boot) still only sees whatever code existed at boot until a restart - unavoidable without also restarting the scheduler itself, but a much smaller, lower-stakes gap than every interactive dev-testing path needing one. **Not low-stakes after a sync-shape change, it turned out:** on 2026-09-29 a server started before Security Simulations Stage 1 kept re-syncing tenants every 30 minutes with the old mapper, overwriting newer-shaped snapshots that manual syncs had just written. After any change to `graph-client.ts`'s sync or mappers, restart (`npm run restart`) before trusting synced data.

**Guard (added 2026-09-29):** live-synced snapshots are stamped with `syncSchemaVersion` (`src/lib/utils/sync-schema-version.ts`, currently 2). `runSync()` reads the stored version *before* fetching (the fetch mutates `existing` in place), and if it's newer than the running build's version it refuses to save, keeps the stored snapshot, and writes a `tenant_sync_failure` audit entry saying to restart the server. **Bump `SNAPSHOT_SYNC_SCHEMA_VERSION` whenever the sync starts storing data an older build would drop.** It only protects builds from version 2 onward; a server older than the guard itself can't know to check.

## Audit Log Investigator storage
Two new tables for [[Audit Log Investigator]] - `ual_imports` (one row per uploaded Purview CSV export) and `ual_records` (one row per ingested audit event, indexed on `(tenant_id, session_id)`/`(tenant_id, user_id)`/`(tenant_id, operation)`/`(tenant_id, creation_date)`). Deliberately a real relational table rather than this file's usual JSON-blob-per-row convention, since a single import can be up to 1,000,000 rows (Purview Audit Premium's own export cap) and needs indexed lookups (a session-ID pivot, a date-range search) that a full JS-side scan over a JSON blob can't do at that scale. `ingestAuditLogCsv()` streams the upload directly into batched (500-row) transactional inserts via `audit-log-parser.ts`'s pure row mapper - the file's content is never materialized as one big JS array. A second globalThis-cached-Map (`auditImportProgressCache`, same pattern as `syncProgressCache` above) tracks live import progress, polled via `GET /api/tenants/[id]/audit-log/import-progress` - it reports a rows-processed counter rather than a percentage, since a streaming parse doesn't know the total row count until it reaches the end of the file (unlike `syncTenant()`'s fixed 17-step progress, which knows its step count upfront).

## Demo CA policy refresh
`backfillSnapshot()` now also refreshes demo tenants' `conditionalAccess.policies`, `namedLocations` and `identitySettings` from `mock-tenants.ts` (added for [[Security Simulations Plan]] Stage 1). Policies are **merged by id, not replaced** (`mergeDemoCaPolicies` in `src/lib/utils/demo-ca-policy-merge.ts`, tested), because `deployBaselinePolicy()` mutates a demo tenant's stored policies locally: it flips an existing policy to report-only or appends a new one. Mock shape wins; the stored state is kept only if it was modified after the mock copy's timestamp; stored-only policies are kept. This is also what repairs already-seeded Woodgrove databases (see [[Baseline Definitions & Mock Data]]).

## Credential rotation
`updateTenant(id, updates)` has always supported rewriting `credentials.clientId`/`clientSecret`/`tenantId` for an existing tenant - the `SECRET_MASK`/`keepExistingSecret` convention (a masked `"••••••••"` value, or none at all, means "leave the stored secret alone"; anything else gets encrypted and stored as the new secret) was originally built for `PermissionsModal.tsx`'s EXO device-code reconnect flow. Until a live incident (an Axiomatic app registration's client secret going bad, breaking every single Graph call tenant-wide with `"Lifetime validation failed, the token is expired"` - see [[Attack Surface Reduction Rules]] for the full investigation trail), **no UI anywhere in the app actually exposed this for an existing tenant** - only `AddTenantModal.tsx` at creation time. `EditTenantCredentialsModal` (see [[Modals]]) is the fix, reachable from the tenant switcher dropdown in `Header.tsx`.

**A second, real bug found rotating that same secret live:** saving a new secret through the new modal appeared to do nothing - the Permissions check kept failing with the exact same error as before the rotation. Cause: [[Core Graph Layer]]'s `getGraphAccessToken()` caches tokens on `globalThis`, keyed by `tenantId:clientId` only - not by the secret - so it kept serving the OLD cached token (acquired under the bad secret) indefinitely, purely because its locally-computed expiry hadn't yet elapsed, with no way to know the underlying credentials had changed. Fixed by a new `invalidateGraphTokenCache()` export, called from `updateTenant()`'s `credentials`-update branch for both the old and new `tenantId:clientId` pair (covers the rare case where those change too, not just the secret) - so any credential edit now forces the next Graph call to authenticate fresh rather than potentially replaying a stale cached failure for up to ~55 minutes.
