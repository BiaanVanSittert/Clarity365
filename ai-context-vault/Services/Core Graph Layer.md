# Core Graph Layer

The Microsoft Graph / Exchange Online integration layer. Four files:

## graph-client.ts :  the master orchestrator
~1230 lines. `fetchLiveTenantSnapshot` is the one function that, on a tenant sync, pulls CA policies, users, directory roles, sign-ins, MFA, Intune, Secure Score, MDO + mailflow (via `exo-client`), domain auth, groups, SharePoint, app registrations, SKUs, ASR rule configuration state (three merged Intune surfaces - see [[Attack Surface Reduction Rules]]), MDE connector settings + per-device onboarding status (steps 18-19, beta - see [[Defender Configuration & Onboarding]]), and incidents :  then hands the result to every [[Data Mappers|mapper]] and [[Baseline Matchers|matcher]] to assemble one `TenantSecuritySnapshot` (see [[Domain Types]]). Also exports `getGraphAccessToken`, `testAppRegistrationPermissions`, `buildGraphCaPolicyPayload`, `deployConditionalAccessPolicy`, `invalidateGraphTokenCache`. `TOTAL_SYNC_STEPS` is now 22 (step 20 is Intune compliance reasons; steps 21-22 were added for Security Simulations, see below).

`invalidateGraphTokenCache(credentials)` deletes the cached token for one `tenantId:clientId` pair - added after a live bug where rotating a tenant's client secret (via [[Tenant Store]]'s `updateTenant()`) had no effect, because `getGraphAccessToken`'s cache is keyed by identity, not by the secret itself, so it kept serving a token acquired under the old (bad) secret until its own locally-computed expiry elapsed. Must be called any time stored credentials change - see [[Tenant Store]] for the call site.

**Second call site: `tenant-store.ts`'s `testPermissions()` now also invalidates the cache before every run**, not just on credential changes. Without it, clicking "Re-Test Permissions" in `PermissionsModal.tsx` right after granting a new permission's admin consent in Entra kept silently reusing the up-to-55-minute-old cached token - consent grants only apply to tokens requested *after* the grant, never to ones already issued, so the modal looked like it wasn't re-checking at all.

**Forcing a genuinely fresh token on every re-test then surfaced a second, real, pre-existing bug: `AuditLog.Read.All` and `Reports.Read.All` occasionally get rejected by Graph's own backend for those two resource providers specifically** with a 401 "Lifetime validation failed, the token is expired," while `Policy.Read.All`/`User.Read.All` succeed with the *identical* token in the same run. A quick live check (decoding that same token's `roles` claim directly) proved both permissions were genuinely granted the whole time - the token itself was fine, only those two resource providers' own gateway was rejecting it. Root-caused this to the same fundamental problem `decodeAppRolesFromToken()` was already built to solve for `isWriteAccess` permissions: **a live per-permission GET/POST probe is simply the wrong tool for "is this permission granted,"** since it can both under- and over-report relative to the token's own `roles` claim. Fixed by generalizing that same fix to every permission in the list, not just the write ones: `testAppRegistrationPermissions()` now checks `isPermissionGrantedByRoles()` (which also handles the few rows listing two Graph-interchangeable alternatives, e.g. `"Reports.Read.All / UserAuthenticationMethod.Read.All"`, granted if either is present) against the decoded token for every permission *except* the four in `PERMISSION_LICENSE_REQUIREMENT` below - those still need a real Graph call, since the roles claim alone can't distinguish "not granted" from "granted but the tenant lacks the underlying license," which `applyLicenseAwareStatus` exists specifically to tell apart. `describeTransientTokenLifetimeError()` remains as a defensive fallback message only for that narrower live-probed set. See the eighth recurring-bug-class entry in [[Optimization Plan]].

**Phase 2 Endpoint Security write path** (see [[Defender Configuration & Onboarding]]/[[Attack Surface Reduction Rules]] for the full picture): `fetchDefenderAvPolicy`/`deployDefenderAvPolicy`, `deployAsrRulePolicy`, `updateMdeConnectorSettings`, plus the pure `buildDefenderAvSettingsPayload`/`buildIntuneAssignmentTarget`/`buildAsrRuleSettingsChildren` - the first functions in this file with actual unit test coverage (`graph-client.test.ts`), closing a small piece of the "no test file" gap below.

**Correction to the "Lifetime validation failed" story above - it is not always a brief transient blip, and retrying with the same token cannot fix it.** A live user report ("EDR deploy stopped working, a different tool can still deploy to the same tenant") forced a deeper dive than the AuditLog/Reports case above got. A standalone script that decrypted Coetzee Architects' real credentials and called Microsoft Graph directly - bypassing Clarity365's own code entirely - succeeded immediately against `deviceManagement/configurationPolicies`, at the exact moment Clarity365's own code was failing against the identical endpoint with the identical error. Tracing further: the token Clarity365's cache was serving (well within its own ~55-minute bookkeeping) was being genuinely rejected by Microsoft's Intune Settings Catalog resource provider specifically, over real network round-trips (a fresh `request-id` from Microsoft on every attempt, ruling out any local caching artifact - `graph-fetch.ts`'s `fetch()` calls now also explicitly set `cache: "no-store"` regardless, since Graph responses should never be cacheable by Next's fetch layer, but that was not the actual bug here). That same token kept working fine for every other Graph resource. Forcing a genuinely fresh token (`invalidateGraphTokenCache` + a new `getGraphAccessToken` call) and retrying resolved it immediately - proving Microsoft can silently invalidate one specific already-issued app-only token for one specific resource provider well before its nominal expiry, and the token's own local cache has no way to detect that on its own.

**Fix: `withFreshTokenOnLifetimeError()`** (new, private to `graph-client.ts`) wraps a whole token-consuming operation - get a token, run the operation, and if the *result* comes back with this specific error, invalidate the cache, get a genuinely fresh token, and retry the entire operation once more. This is a different fix from `graph-fetch.ts`'s own short retry (which retries the *same* request with the *same* token, useful only for the brief-blip case, and useless here since the token itself is the problem). Applied to the five functions actually affected: `fetchEdrPolicy`, `deployEdrPolicy`, `fetchDefenderAvPolicy`, `deployDefenderAvPolicy`, `deployAsrRulePolicy` - each split into an outer mock-check + wrapper call and an inner `*WithToken` function carrying the real logic, so the wrapper's `operation: (token: string) => Promise<T>` shape can call back into it. **Not yet applied to `fetchLiveTenantSnapshot`'s other ~20 Graph calls** (CA policies, users, directory roles, sign-ins, MFA, Secure Score, MDO, groups, SharePoint, app registrations, SKUs, incidents, MDE connector/onboarding, ASR's own read path) - same manual `getGraphAccessToken` + `graphFetch` pattern throughout, equally exposed to this bug on whichever resource Microsoft treats the same way, just less frequently hit in practice so far. Same fix, same wrapper, is the natural next pass once this one is confirmed stable. Regression tests in `graph-client.test.ts` (`describe("withFreshTokenOnLifetimeError (via fetchEdrPolicy)")`) mock only the network boundary (`global.fetch`) and exercise the real `getGraphAccessToken`/`graphFetch`/`fetchEdrPolicy` stack end-to-end - one confirms the fresh-token retry fires and succeeds, one confirms a real unrelated error (403) does *not* burn a second token.

`testAppRegistrationPermissions`' self-test loop supports a per-permission `method`/`body` override (defaulting to plain GET) so a permission with no GET-able Graph surface can still be tested - `ThreatHunting.Read.All` (Advanced Hunting is POST-only) is the one permission that needs this today. Every tested permission carries an `optional` flag, excluded from the pass/fail rollup, so declining an optional permission (currently: this one and the CA write permission - just two now, see below) never shows as a problem. `PermissionsModal.tsx` also always renders `isWriteAccess` permissions last in both the optional-permission summary and the main table, via a stable sort over `report.permissions` - independent of whatever order this array returns them in, so a future write-capable permission added anywhere in the list still lands at the bottom automatically.

Also cross-checks every "missing" result against the tenant's actual licensed capabilities (`capabilities-mapper.ts`'s `mapSubscribedSkusToCapabilities`, via one extra `/subscribedSkus` call - **no `$top`/`$filter` on that endpoint, it doesn't support them and silently misbehaves if you add them**, confirmed the hard way) before reporting it as a plain "missing permission" - see `permission-license-check.ts`'s `PERMISSION_LICENSE_REQUIREMENT` map and [[Attack Surface Reduction Rules]]/[[Intune Endpoint Security]] for why a missing license and a missing consent grant need different messaging (granting the Graph permission fixes one, not the other).

**`Application.Read.All` (CA05's extra requirement) was removed as its own checked permission** - it used to be a fourth optional entry with its own row/description, but per explicit user feedback ("not so many separate permissions and texts when it is not needed") that was one edge case (out of ten CA baselines) getting equal billing with permissions every module actually depends on. Its explanation is now folded into `Policy.ReadWrite.ConditionalAccess`'s own description as a one-sentence caveat, and the actual moment it matters - a CA05 deploy attempt - is where it's now surfaced: `deployConditionalAccessPolicy()` pattern-matches CA05's two known failure modes (missing `Application.Read.All` → a 403/`Authorization_RequestDenied`-shaped error; the target service principal not existing in the tenant yet → Graph's `ServicePrincipalNotFound`) and rewrites Graph's raw error into the specific fix for each, rather than proactively listing the permission in every tenant's report whether or not anyone's about to deploy CA05. See [[Conditional Access Policy Scanner]] for both failure modes in full.

**Three optional permissions now**, not two: `ThreatHunting.Read.All`, `Policy.ReadWrite.ConditionalAccess`, and `DeviceManagementConfiguration.ReadWrite.All` (added for [[Defender Configuration & Onboarding]]/[[Attack Surface Reduction Rules]]'s Phase 2 write path - MDE connector setting changes, Defender Antivirus policy deployment, ASR rule deployment).

**Every `isWriteAccess` permission is now checked by decoding the access token's own `roles` claim, not by a live GET probe.** `DeviceManagementConfiguration.ReadWrite.All` used to be tested the same way as its `.Read.All` counterpart - GETting `deviceManagement/intents?$top=1` - which is exactly the bug: Microsoft Graph's own least-privilege table accepts that GET with *either* the Read.All or ReadWrite.All role, so a tenant with only Read.All granted still showed the write permission as "Granted." Caught live on Coetzee Architects (Permissions modal said granted; the actual EDR policy deploy failed with "Application is not authorized to perform this operation"). `decodeAppRolesFromToken()` base64url-decodes the JWT payload and checks its `roles` array directly - app-only (client-credentials) tokens list every granted app role regardless of which endpoint the token is later used against, so this is both side-effect-free and immune to any single endpoint's own least-privilege ambiguity. `testAppRegistrationPermissions()` decodes the token's roles once per run and reuses it for every `isWriteAccess` entry (currently `Policy.ReadWrite.ConditionalAccess` and `DeviceManagementConfiguration.ReadWrite.All`); a decode failure falls back to the old live-probe path rather than misreporting "missing." See the seventh recurring-bug-class entry in [[Optimization Plan]].

Also exports `fetchAsrDetectionSummaries`/`fetchAsrDetectionEvents` for [[Attack Surface Reduction Rules]] - notably **not** called from `fetchLiveTenantSnapshot`, the one pair of Graph functions in this file deliberately kept out of the main sync (on-demand only, since `security/runHuntingQuery` needs the separate `ThreatHunting.Read.All` permission + a Defender for Endpoint P2 license many tenants won't have consented to, and would slow down every sync for one module's data otherwise). Both follow `deployConditionalAccessPolicy`'s mock-short-circuit-first shape; the live path shares an internal `runHuntingQuery()` helper that POSTs to `v1.0/security/runHuntingQuery` (not beta) and normalizes Graph's camelCase result rows.
**Mostly untested** :  the largest, most critical, most fan-out file in the codebase has only a narrow `graph-client.test.ts` covering the handful of pure functions listed above - every live-Graph-calling function (the sync itself, every deploy function) is still untested. See [[Testing]].
Also resolves per-user `assignedLicenses` `skuId` GUIDs to `skuPartNumber` names (e.g. `"SPE_E5"`) using the tenant-wide `subscribedSkus` fetch, right after that fetch completes :  a post-processing remap of `usersList`, not a reordering of the sync. Required for [[Data Mappers]]'s `admin-hygiene-matcher` to recognize licenses on live tenants (mock data already uses friendly names).

CA policy mapping now carries through `conditions.locations`, `conditions.platforms`, `conditions.userRiskLevels`, `conditions.signInRiskLevels`, and `conditions.users.includeRoles` from the raw Graph response :  these were silently dropped before, which broke CA06/CA07/CA08's (and admin-role-targeted CA03/CA10's) re-validation against the stored snapshot on live tenants even though the initial sync-time classification was correct. `grantControls.authenticationStrength` (a sibling of `builtInControls`, not part of it) is encoded as an `"authenticationStrength:<name>"` marker string appended to the `grantControls` array, matching this app's own convention (see [[Baseline Matchers]]'s `hasAuthStrengthOrSession`). Also fixed: the `RoleManagement.Read.Directory` permission-test endpoint used `?$top=1`, which Graph's `/directoryRoles` doesn't support (`HTTP 400`) :  reported as a missing permission regardless of what was actually granted.

Also fixed: the `/users` fetch now selects `signInActivity`, whose `lastSignInDateTime` is Graph's authoritative "last interactive sign-in" (requires `AuditLog.Read.All`, already held for `auditLogs/signIns`). The MFA-profile mapping previously hardcoded `lastSignInDateTime: new Date().toISOString()` as a fallback :  every user, including ones who had never signed in, showed "Today" in [[Tenant License Optimization]] and [[Fleet License Optimization]]. Now it prefers the real `signInActivity` value, falls back to the most recent matching `auditLogs/signIns` event, and finally `""` (never signed in) :  never the current timestamp.

The `/subscribedSkus` fetch (used for `capabilitiesLive` and the `skuId -> skuPartNumber` map) now also builds `licenseSkusLive: TenantLicenseSku[]` (`consumedUnits`, `prepaidUnits.enabled`, and the derived `availableUnits` gap) and assigns it to `base.licenseSkus`. This is what [[Analysis & Generation]]'s `calculateTenantMonthlyWaste` prices out as the `unassigned_license_sku` waste category :  previously the type/summary plumbing existed end-to-end but no code ever populated it, so purchased-and-unassigned seats never appeared anywhere in the license optimizer.

**Security Simulations Stage 1 (2026-09-29, see [[Security Simulations Plan]]).** `mapConditionalAccessPolicy()` now spreads in `ca-environment-mapper.ts`'s `mapCaPolicyExtendedFields()`, keeping fields it used to drop: `includeGroups`, `excludeRoles`, guest types, `includeUserActions`, authentication-context references, `authenticationFlows` (device code / authentication transfer), `insiderRiskLevels`, `devices.deviceFilter` (stored, never parsed), workload-identity `clientApplications`/`servicePrincipalRiskLevels`, `grantControls.operator` (AND/OR) and v1.0 `sessionControls`. Two new sync steps:
- **21, named locations and beta session extras**: `GET v1.0 identity/conditionalAccess/namedLocations` (resolves the location GUIDs on each policy to countries or IP ranges). Then a best-effort `GET beta .../policies?$select=id,sessionControls`, because **token protection (`secureSignInSession`) and continuous access evaluation exist only on beta**; v1.0's `conditionalAccessSessionControls` has only five properties (confirmed on Microsoft Learn 2026-09-29). The beta read is deliberately not a sync error: on failure those two fields stay undefined ("not assessed"), never false.
- **22, tenant identity settings**: three single-object reads, `policies/identitySecurityDefaultsEnforcementPolicy`, `policies/authorizationPolicy` (user consent, guest role, guest invites) and `policies/adminConsentRequestPolicy`, each failing independently.
All use `Policy.Read.All`, which is already requested and self-tested, so no new consent is needed. **Verified live 2026-09-29** on three tenants (the others were overwritten by a stale dev-server scheduler; see [[CA Simulation Engine]]).

Stage 2 follow-ups: the directory-roles step now also records each member's role **template id** (`UserMfaProfile.adminRoleTemplateIds`), because CA targets roles by template GUID. And `applyCaBetaSessionExtras` sets `tokenProtection: false` explicitly for every policy the beta read returned, so `undefined` only ever means "beta not read".

**Security Simulations Stage 5 (2026-09-30):** three more steps (23 Exchange audit & legacy protocol settings, 24 privileged role assignments with PIM state, 25 OAuth consent grants), `TOTAL_SYNC_STEPS` = 25, and the SharePoint step now keeps the rest of `admin/sharepoint/settings` (see [[Security Simulations Plan]] Stage 5 record). Snapshot schema version 3. Post-verification fixes: PIM calls no longer use `$expand=principal` (principals resolved from synced users/groups, `pimUnavailableReason` recorded), and a missing OAuth-grant permission is stored as `oauthConsentGrants.unavailable` rather than a sync error. The permission self-test gained an optional **"DelegatedPermissionGrant.Read.All / Directory.Read.All"** row. Note: v1.0 `sharepointSettings` has no default link type or Anyone-link expiry, so `mapTenantSharingSettings`'s values for those two have always been placeholders on live tenants (`linkDefaultsReported: false`).

## scc-client.ts :  Security & Compliance PowerShell (read-only)
Reads Microsoft 365 alert policies as the app registration itself, with the client secret, no sign-in. Only ever invokes `Get-ProtectionAlert`. Same prerequisite as Exchange app access (Exchange.ManageAsApp + a role such as Global Reader); a token without that role, or a 401/403, comes back as `unavailable: "notSetUp"`.

Routing is observed behaviour, not documented by Microsoft: the global host `ps.compliance.protection.outlook.com` can't serve a tenant directly. POSTed with `X-AnchorMailbox: UPN:SystemMailbox{bb558c35-...}@<initial onmicrosoft domain>` (read from Graph `organization.verifiedDomains`), it answers 302 to `<region>.admin.protection.outlook.com:446`, which isn't reachable; the read then goes to `<region>.ps.compliance.protection.outlook.com`. Token and region are cached in memory; a failed regional read drops the cached region. If Microsoft changes the routing the result is `unavailable: "error"`, never an empty list. Tested in `scc-client.test.ts` with only `fetch` mocked. `alert-policy-mapper.ts` holds the pure mapping and matching.

## exo-client.ts :  Exchange Online
**App-only first (2026-09-30):** every cmdlet now authenticates as the app registration itself (client secret, scope `https://outlook.office365.com/.default`) when it has Exchange.ManageAsApp and an Entra role, and only falls back to the delegated device-code token when that isn't set up. See [[Exchange App-Only Access Plan]] and `exchange-access.ts`. OAuth device-code flow + `invokeExoCommand`, `fetchMdoPoliciesAndTabl`, `fetchMailflowData`, `fetchAcceptedDomainsAndDkim`, `fetchExchangeSecuritySettings` (Stage 5), TABL writes, `disableForwardingRule`, `removeMailboxDelegation`, `setMailboxAuditingEnabled`.

**Refresh-token rotation (2026-09-30):** `getExoAccessToken` records each rotation old → new (`resolveLatestExoRefreshToken`) so a caller holding a stale tenant object still uses the newest token, and de-duplicates concurrent refreshes per tenant. A brand-new token from reconnecting is used as-is. `exo-client.test.ts` covers this (the file's first tests); the live EXO writes and device-code flow remain untested. See [[Testing]].
