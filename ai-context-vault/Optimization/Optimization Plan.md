# Optimization Plan

Grounded in the scan behind this vault (see [[Clarity365 MOC]]). Ordered by risk, not effort.

## P0 :  Before you run the updated app at all
1. ~~**Create `.env.local`** with `CLARITY365_SESSION_SECRET` and `CLARITY365_ENCRYPTION_KEY`~~ :  **fixed at the root, not just worked around.** This had surfaced exactly as predicted on a manually-patched machine: operator password setup succeeded (it only needs `crypto.hashPassword`), but login failed with `CLARITY365_SESSION_SECRET is not set` because `auth.createSessionToken` had nothing to sign with. Manually creating `.env.local` fixed that one machine but not the underlying gap :  a fresh clone anywhere else hit the identical failure, confirmed when reproduced during this repo's initial clone. `scripts/ensure-env.js` now runs as a `predev`/`prebuild`/`prestart` hook and generates both secrets into `.env.local` automatically the first time either is missing, so no manual step is needed on any machine. **Still store these two values in a password manager once generated** :  `.env.local` is gitignored (never committed) and losing `CLARITY365_ENCRYPTION_KEY` after tenants are added makes their stored secrets permanently unreadable. See [[Security & Auth]].
2. **The 5 high-severity `npm audit` findings all trace back to `next@14.2.15` itself** (DoS, SSRF, cache-poisoning, and XSS advisories in Next's Image Optimizer, Server Actions, and Middleware :  [full list](https://github.com/advisories/GHSA-9g9p-9gw9-jx7f) and siblings) plus its transitive `postcss` and `glob`/`eslint-config-next` chain. **`npm audit fix --force` would jump `next` 14 → 16** :  a major-version App Router upgrade, not a patch. Don't run that blind: read the Next.js 15 and 16 migration guides first, since this app leans on `middleware.ts` (Edge runtime) and `instrumentation.ts`, both areas that changed across those majors. Treat this as a planned upgrade task, not a one-command fix :  but don't leave it indefinitely either, since several of these are real internet-facing DoS/SSRF classes (lower stakes here since the app is `127.0.0.1`-bound, but worth closing before any future LAN/WAN exposure is considered).
3. **Review the two pending install scripts** (`better-sqlite3`, `unrs-resolver`) with `npm approve-scripts --allow-scripts-pending` before approving :  both are legitimate, but this is the first time either has run in this repo.

## P1 :  Highest blast-radius code, near-zero test coverage
These four files can each affect *every* tenant or *the login gate itself* on a bug, and (mostly) have no tests (full gap list in [[Testing]]):
- `auth.ts` :  the entire session-verification boundary. A subtle bug here is an auth bypass, not a crash.
- `fleet-operations.ts` :  one call touches every tenant in the fleet ([[Fleet Baseline Rollout]], [[Fleet TABL Sync]], [[Fleet Baseline Drift]] all funnel through it). The UI already gates these behind [[Modals#ChangeConfirmationModal|ChangeConfirmationModal]], which protects against fat-fingering but not against a logic bug in what the confirmed action actually does.
- `graph-client.ts` / `exo-client.ts` :  the only files that make live writes to a real customer's M365 tenant. `graph-client.ts`'s `graph-client.test.ts` has grown well past its original narrow payload-builder scope (`buildDefenderAvSettingsPayload`, `buildIntuneAssignmentTarget`, `buildAsrRuleSettingsChildren`) - it now also covers `withFreshTokenOnLifetimeError` (via `fetchEdrPolicy`), `createSettingsCatalogPolicyReplacing` (via `deployEdrPolicy`), `fetchBitLockerPolicy`/`deployBitLockerPolicy`, and `mapConditionalAccessPolicy` (the CA-policy read-mapping/classification step - see [[Conditional Access Policy Scanner]]'s CA04 fix), all with mocked `fetch`. `exo-client.ts` still has zero tests, and `graph-client.ts`'s actual sync/deploy orchestration functions (`fetchLiveTenantSnapshot`, the various `deploy*Policy` functions themselves) remain untested end-to-end - only the pure mapping/payload-building pieces pulled out of them are.

Recommendation: write tests for these four before adding new fleet-wide features, not after. A dry-run mode for `fleet-operations.ts` (compute + return the diff without writing, reusable by both the confirmation modal's preview and a test) would let you test the risky part without needing live tenants.

## P2 :  Structural
4. **`tenant-store.ts` (~1700 lines) is the transitive dependency of every route.** Not urgent, but the next time you're in there for an unrelated change, consider splitting by concern (tenant CRUD / CA operations / incident-response / TABL / settings-and-auth-config) behind the same call sites :  a targeted change today touches a file that also holds unrelated logic for 20+ other features.
5. **Baseline auto-fix coverage is uneven** (see [[Baseline Definitions & Mock Data]]): CA 10/10, MDO 8/9, Mailflow 5/8, Groups 0/7, SharePoint 0/5. If Groups/SharePoint auto-fix is on the roadmap, that's a concrete backlog. If it's deliberate (unconfirmed write paths, judgment calls :  as the code comments suggest), a one-line note in each definitions file saying so would stop a future contributor from "fixing" what isn't broken.
6. **No UI/component tests** across 24 modules. Not asking for full coverage :  but the handful of modules with a live-write confirmation flow ([[Event Response (Incident Response)]], [[Fleet Baseline Rollout]]) are the ones where a regression is costliest, and would benefit most from even a thin smoke test.
7. **Recurring bug class: duplicated classification/derivation logic drifting apart across call sites.** Five separate live bugs this project has hit trace back to the same root cause :  the same piece of "what does this state mean" logic re-implemented inline in two or more places, which then silently disagree once one copy changes and the other doesn't: `Tenant.connectionStatus` display (Fleet Posture Matrix vs. header, fixed by `getConnectionStatusDisplay()`), CA baseline naming/settings matching (fixed by `classifyCaBaselineCode()`), the sign-in logs badge watermark (`Sidebar.tsx`'s `saveDismissedState()` blind-overwriting a co-located field instead of merging), MDE/Defender-for-Endpoint capability detection (`AsrRulesModule.tsx`'s gate only recognized mock-only capability ids, never the live mapper's generic `cap-mde`, fixed by the shared `hasDefenderForEndpointCapability()` in [[Attack Surface Reduction Rules]]), and - predicted right here as "a fifth instance" before it actually happened - Entra ID P2 detection, duplicated identically in `ConditionalAccessModule.tsx` and `drift-analyzer.ts`, both checking a mock-only id and a name-substring pattern that never matched a live tenant's real generic `cap-entra` id/tier, fixed by the shared `hasEntraP2Capability()` in `src/lib/utils/entra-p2.ts` (see [[Conditional Access Policy Scanner]]). Recommendation: when adding a new module or sidebar element that needs to re-derive a status/tier/gate another component already computes, extract a shared pure function (and test it) from the start rather than copying the inline check :  this is now the established convention (see `tenant-connection-status.ts`, `ca-baseline-matcher.ts`, `sign-in-review-watermark.ts`, `defender-for-endpoint.ts`, `entra-p2.ts` as the fixed examples), but nothing currently prevents a sixth instance - the pattern to watch for specifically: a capability check written against mock data's tier-specific id (`cap-x-p1`/`cap-x-p2`) that was never actually verified against what `capabilities-mapper.ts` produces for a live tenant (always one generic `cap-x` id, tier-distinguished only by its `tier` string field).
   - **A closely related but distinct class, also now closed once:** a feature can ship with a complete UI and convincing mock data while its live-data half was simply never built, and look finished in every demo regardless. ASR rule *configuration* reporting shipped this way - `AsrRulesModule.tsx` and 4 mock tenants existed for a full session before any code fetched real configuration from a live tenant, so every live tenant silently showed all 19 rules as Not Configured. Closed by the three-surface live fetch documented in [[Attack Surface Reduction Rules]]. Worth checking for on any future module: does mock data alone make this look done?
   - **A third related-but-distinct variant: the same *wrong* value copy-pasted into every call site, so nothing ever disagreed with itself.** CA01's `clientAppTypes` used the invalid Graph enum value `"otherClients"` (real value: `"other"`) identically in nine places - the live deploy payload, two PowerShell script templates, the compliance matcher's expected-value set, the mock fixture, and three local snapshot-realignment payloads - so mock data, the matcher, and every demo all agreed with each other and looked correct. Only a real deploy attempt against live Microsoft Graph surfaced it (error `1007`, schema mismatch), since Graph itself was the only thing in the loop that actually validated the value. See [[Conditional Access Policy Scanner]]. The tell for this variant: consistency across every copy is not the same as correctness - when a literal value (an enum member, a GUID, a magic string) is duplicated instead of imported from one constant, a wrong value survives precisely because nothing ever compares it against an authoritative external source until a live call is actually made.
   - **A fourth variant: a permission self-test's probe query conflated "permission not granted" with "this specific query failed for an unrelated reason," reporting both as one "missing" outcome.** [[Attack Surface Reduction Rules]]'s `ThreatHunting.Read.All` self-test queried the real `DeviceEvents` table directly and treated any non-2xx response as "missing" - so a tenant with the permission genuinely granted still got a false "missing permission" report, because the probe query itself failed for a reason having nothing to do with the permission grant (a 400/401 being read the same as a real 403 auth failure). Fixed by making the self-test probe table-independent (a bare `print` literal, no table reference at all) so the result reflects only the permission grant, and by giving the real query's error handling (`classifyAdvancedHuntingError()`) distinct rewrites per failure shape instead of one generic error path for all of them. The tell for this variant: when a self-test's probe exercises more than the one thing it's testing, any failure gets misattributed to the thing being tested even when the real cause is unrelated - a permission self-test's probe should be the minimum possible surface, not a realistic example of the feature. **Follow-up correction:** the first fix's own error-rewrite confidently named "Defender for Business lacks this table" as the cause of the 400 - itself a second instance of the same overconfidence this variant is about, disproven live by a user whose Defender-for-Business tenant could see the same data in the Defender portal directly. See [[Attack Surface Reduction Rules]] for the corrected, non-committal message and what the live investigation found instead (a 401 "lifetime validation failed" error, confirmed not to be Clarity365's own caching, with the real Microsoft-side cause still unconfirmed).
   - **A fifth variant, caught before it shipped rather than after: a planning-stage assumption that two similar-looking Graph surfaces share a mechanism when they don't.** [[Defender Configuration & Onboarding]]'s Phase 1 plan assumed Defender Antivirus policy settings would reuse ASR's Settings Catalog "slug-map" resolution (`getAsrSettingsCatalogSlugMap`), generalized to a second root category - because both are Settings Catalog Defender settings, they looked interchangeable from a distance. They aren't: ASR is one collection setting with many rule-GUID children that genuinely need runtime resolution against Microsoft's own catalog metadata (the GUIDs aren't documented); Defender AV settings are ~18 independent, already-documented flat `settingDefinitionId` strings needing no dynamic lookup at all. Caught during Phase 2 planning (before any code was written) by re-verifying the actual Graph payload shapes against Microsoft's docs instead of trusting the Phase 1 plan's own wording - see the correction recorded directly in the Phase 2 plan and in [[Defender Configuration & Onboarding]]. The tell for this variant: two things that use the same underlying technology (here, Settings Catalog) are not automatically the same *shape* of problem - re-verify the specific mechanism, not just the category, before reusing code across them.
   - **A sixth variant: a name-based match against Microsoft's own catalog metadata silently broke tenant-wide when Microsoft changed the wording it matches against.** [[Attack Surface Reduction Rules]]'s `buildAsrSlugMap()` matches Settings Catalog displayNames against `ASR_RULE_DEFINITIONS`' hardcoded names after normalizing (stripping non-alphanumeric characters). A live tenant's catalog data was found (mid-session, verifying an unrelated feature) to now carry a `" (Device)"` suffix on every ASR rule displayName that survives normalization and breaks every single match (0/19) - a real, tenant-side Microsoft wording change, not a code regression from this session. Not yet fixed - see the note in [[Attack Surface Reduction Rules]] for the two candidate fixes (strip the suffix, or match on the settingDefinitionId's slug instead of displayName). The tell for this variant: matching against a human-readable label Microsoft controls (as opposed to a stable machine id) is inherently fragile to wording changes outside this app's control - prefer matching on `settingDefinitionId`/`rootDefinitionId` over `displayName` wherever both are available, even though displayName matching is what let the original ASR slug-map be built in the first place (the GUIDs genuinely aren't documented any other way).
   - **A seventh variant: a permission self-test's live GET probe passed on a weaker permission than the one it claimed to test.** `testAppRegistrationPermissions()`'s `DeviceManagementConfiguration.ReadWrite.All` check GETs `deviceManagement/intents` - an endpoint Microsoft Graph's own least-privilege table accepts with *either* `DeviceManagementConfiguration.Read.All` or the `.ReadWrite.All` variant. A live tenant (Coetzee Architects) had only the Read.All role granted, so the GET succeeded and the Permissions modal showed the write permission as "Granted," while the actual EDR policy deploy failed with "Application is not authorized to perform this operation." The same class of bug as the fourth variant above (a probe exercising more than the one thing it's testing), but inverted: that one over-attributed unrelated failures to a missing permission; this one under-attributed a real missing permission because a *read* verb satisfied a *write* check. Fixed by decoding the `roles` claim directly out of the access token's JWT payload for every `isWriteAccess` permission (`decodeAppRolesFromToken()` in `graph-client.ts`) instead of live-probing it - app-only tokens list every granted app role regardless of which endpoint the token is later used against, so this is both side-effect-free and immune to any endpoint's own least-privilege ambiguity.
   - **An eighth variant, found immediately after fixing the seventh: the live probe also failed in the OPPOSITE direction for two permissions that were never in question.** Fixing variant seven required `testPermissions()` to force a genuinely fresh access token on every re-test (previously it silently reused one up to ~55 minutes old, so a just-granted consent never showed up until the cache happened to expire - see [[Core Graph Layer]]). That fresh token then revealed that Graph's `AuditLog.Read.All` and `Reports.Read.All` resource providers specifically reject a *brand-new* token with a 401 "Lifetime validation failed, the token is expired," while `Policy.Read.All`/`User.Read.All` succeeded with the byte-identical token in the same run - proof it wasn't the token, confirmed by decoding that token's `roles` claim directly and finding both permissions genuinely present. The user saw this as "other permissions disappeared" after the variant-seven fix shipped. Root cause: this was the exact same "a live GET probe is the wrong tool for answering 'is this permission granted'" problem as variant seven, just manifesting as an unrelated backend quirk instead of a too-lenient endpoint. Fixed by generalizing the variant-seven fix to *every* permission, not just `isWriteAccess` ones: `isPermissionGrantedByRoles()` checks the decoded token's roles claim for anything not in `PERMISSION_LICENSE_REQUIREMENT` (the small set - `ThreatHunting.Read.All`, `SecurityAlert.Read.All`, the two Intune ones - that genuinely needs a live call, since only Graph itself can tell "not granted" apart from "granted but unlicensed" for those). The tell for both variants together: once you've established a token's own claims are the authoritative answer to "what is this app allowed to do," a live call to a specific resource endpoint is answering a *different*, noisier question ("did this one call succeed right now") that should only be trusted when there's a genuine reason (like a license cross-check) that the claims alone can't resolve - default to the claims, not the call, for a pure consent check. Worth checking `Policy.ReadWrite.ConditionalAccess`'s self-test too if a similar issue is ever reported there (it's already covered by this same fix, being `isWriteAccess: true`).
   - **A ninth variant: the same "Lifetime validation failed" error from variant eight turned out not to always be the brief, self-resolving blip it was assumed to be - and the previously-shipped fix (retry the same request) could never have recovered from this version of it.** A live user report - "EDR deploy stopped working, a different tool still deploys to the same tenant fine" - forced re-opening a question this vault had treated as settled. A standalone script that called Microsoft Graph directly with the tenant's real credentials, bypassing Clarity365's own code entirely, succeeded immediately against the exact endpoint Clarity365 was failing against at that exact moment. Tracing further: Clarity365's cached token (well within its own bookkeeping's validity window) was being genuinely rejected by Microsoft's Intune Settings Catalog resource provider specifically, over real network round-trips, while that same token kept working for every other resource - and forcing a real fresh token fixed it instantly. The tell this adds to variant eight's: a plausible, even partially-correct explanation for one instance of an error ("brief backend propagation delay, retry and it clears") is not evidence that every future instance shares the same shape - this version could persist for many minutes across dozens of same-token retries and never once self-resolve, because retrying the same request only re-asks Microsoft to validate the same already-rejected token. Fixed by `withFreshTokenOnLifetimeError()` in `graph-client.ts` - see [[Core Graph Layer]] for the full mechanism and the five functions it's applied to (`fetchEdrPolicy`, `deployEdrPolicy`, `fetchDefenderAvPolicy`, `deployDefenderAvPolicy`, `deployAsrRulePolicy`). **Not yet extended to `fetchLiveTenantSnapshot`'s other ~20 Graph calls**, which share the identical manual token-then-fetch pattern and are equally exposed - flagged there as the natural next pass, not done yet.
   - **A tenth variant, a different shape entirely: adding a new required field to a hub type crashes on data persisted before that field existed, because `TenantSecuritySnapshot` has no schema-migration system.** Adding `SecureScoreControl.deployment` (see [[Secure Score & Timeline]]) crashed the whole module on `ctrl.deployment.type` (undefined) for Coetzee Architects - a real tenant whose snapshot was last synced before the field existed - live-reproduced in the browser before being fixed. `TenantSecuritySnapshot` is written to `data/clarity365.db` as an opaque JSON blob and read back as-is; nothing backfills or versions it between app updates. Fixed narrowly (a `withLegacyDefaults()` normalizer at the top of `SecureScoreModule.tsx`), not fixed structurally - the next new required field added anywhere on this snapshot (not just Secure Score) will reproduce this exact crash for every tenant that hasn't re-synced since, unless its own consumer adds the same kind of defensive default. Worth a real migration/versioning layer if this keeps happening; until then, treat "does old persisted data have this field" as a checklist item whenever a required field is added to anything under `TenantSecuritySnapshot`.
   - **An eleventh variant: Microsoft silently moved a condition from a deprecated flat string into a structured field, and a live GET only ever returns the new shape - breaking a matcher that only ever checked the old one.** [[Conditional Access Policy Scanner]]'s `targetsGuests()` only checked for the literal string `"GuestsOrExternalUsers"` inside `conditions.users.includeUsers`. Graph still silently accepts that deprecated string on policy creation and auto-upgrades it, but a live GET of the resulting policy never returns it again - the real condition lives in a separate `includeGuestsOrExternalUsers` object instead, which `targetsGuests()` never looked at. A live user report ("CA04 shows Misconfigured") traced to this directly: the deployed policy was correct and Microsoft was enforcing it correctly the entire time, only Clarity365's own re-classification was blind to it. The tell for this variant, distinct from the others above: the bug isn't a wrong value or a dropped field during *this app's own* mapping pass alone (though that happened too, as a second symptom of the same root cause) - it's that the *external* API's own accepted input shape and returned output shape silently diverged, and nothing forced a re-check of a matcher written against the older shape. Worth specifically re-verifying anywhere else this codebase checks a Conditional Access condition by inspecting a plain string value inside `includeUsers`/`excludeUsers` rather than the correct structured sibling field - `includeRoles` already gets its own array, but any other "special" user-target string value is worth a live double-check the same way this one got one.

## Planned feature work
- **DLP and sensitivity labels** (not started): see [[DLP & Sensitivity Labels Plan]] and [[DLP Stage 1 - Data Model & Licensing]]. Two gaps found while planning, both latent today and both independent of whether the feature ships:
  - ~~**Stale in-memory EXO refresh token during a sync.**~~ **Fixed 2026-09-30** in `getExoAccessToken` (rotation chain + one in-flight refresh per tenant; see [[Core Graph Layer]]). Original note: `getExoAccessToken()` rotates the refresh token and the callback persists the new one to SQLite, but the `tenant` object threaded through `fetchLiveTenantSnapshot` (graph-client.ts, the MDO, mailflow and domain-auth steps) is never updated. Hidden by the ~55-minute access-token cache; it would surface as soon as a second Microsoft resource token (Purview compliance) is requested, or if a sync ever outlived the cache. Fix: wrap the callback so it also updates a local copy passed to every EXO step.
  - **`capabilities-mapper.ts` `hasPurview` is E5-only** (`ADVANCED_AUDITING`, `COMPLIANCE`, `INFORMATION_PROTECTION`, `SPE_E5`) and reports tier "Standard" (`licensed: false`) for E3 and Business Premium tenants, which do include DLP for Exchange, SharePoint and OneDrive plus manual sensitivity labels. No code gates on `cap-purview` today, so it is harmless now, but any future gate would wrongly hide the feature from those tenants. Also relevant: `/subscribedSkus` `servicePlans` are discarded by the sync, so licence detection is SKU-name substring matching only. **Confirmed live 2026-09-21 on Crimson Line Live Demo** (`DEVELOPERPACK_E5`, a Microsoft 365 E5 developer subscription whose service plans all provision successfully): the stored capabilities mark Purview, Defender for Office 365, Defender for Endpoint and Intune all unlicensed, because that SKU name matches none of the substring lists. Not specific to Purview; any Microsoft 365 developer-program tenant is affected.
- **Device Secure Score guides - complete.** See [[Secure Score & Timeline]]'s 2026-09-22 entries for the full sequencing. `device-secure-score-guides.ts` now covers all 113 non-ASR Device-category controls: Defender AV/EDR/Firewall/SmartScreen (31), BitLocker/TPM/Credential Guard/VBS/LAPS (13), and Windows local security policy hardening - password/lockout, UAC, SMB/NTLM/LDAP, RDP/WinRM/Remote Assistance, Netlogon, network/ICS hardening, local accounts, service-account hardening, AutoPlay, browser policy, and the mshta.exe firewall block (69). The 18 ASR rules are deliberately not duplicated - already covered by [[Attack Surface Reduction Rules]]. No further groups pending.

- **Security Simulations** (Stages 1-2 of 7 built 2026-09-29): see [[Security Simulations Plan]] and [[CA Simulation Engine]]. New process gap found: a long-running dev server's scheduler silently overwrote new-shape synced data with old-shape data (see [[Tenant Store]]). **Fixed the same day:** snapshots are now stamped with a sync-schema version and a build refuses to overwrite a snapshot from a newer build (see [[Tenant Store]]). Remember to bump `SNAPSHOT_SYNC_SCHEMA_VERSION` whenever the sync shape grows. The CA mapping gap below is now closed by Stage 1; kept here as the record of why. Found while planning: `mapConditionalAccessPolicy()` drops `includeGroups`, `excludeRoles`, `includeUserActions`, `authenticationFlows`, `insiderRiskLevels`, `grantControls.operator` and all `sessionControls`, and named locations are never fetched, so location GUIDs can't be resolved to countries. Any feature that reasons about which policy applies to whom is currently working from an incomplete policy.

- **SharePoint link defaults were never real on live tenants** (found 2026-09-30): `mapTenantSharingSettings` reads `sharingLinkDefaultType` and `anonymousLinkExpirationRestrictionDays`, which v1.0 `sharepointSettings` doesn't have, so every live tenant showed "Internal" / 0 days regardless of its actual settings. Now flagged by `SharePointTenantPolicy.linkDefaultsReported: false`; the SharePoint module and baseline (SP checks using `defaultLinkType` / `anonymousLinkExpirationDays`) still treat the placeholders as real and should check that flag. Same bug class as the "mock data makes it look finished" variant.

- **Exchange app-only access** (built 2026-09-30, client-secret option): see [[Exchange App-Only Access Plan]]. Consolidated ~20 separate `exoRefreshToken` checks into `exchange-access.ts`. Remaining: first live write under Exchange Administrator, optional certificate upgrade.

- **Recommendations after Security Simulations** (2026-10-01, for review): see [[Recommendations Plan]]. Headline: every live tenant is permanently "degraded" because two sync steps need permissions that no list asks for.
