# Conditional Access Policy Scanner

CA01 to CA10 baseline policy scanner with report-only detection. The original flagship module.

- **Component:** `ConditionalAccessModule.tsx`
- **Reads:** `TenantSecuritySnapshot.conditionalAccess` (prop-driven, no direct fetch)
- **Key types:** `CAPolicyRule`, `CABaselineItem` :  see [[Domain Types]]
- **Uses service:** [[Baseline Matchers]] (`ca-baseline-matcher` :  the most depended-on file in the codebase)
- **Renders:** `StatusPill`, [[Modals#DeployCaPolicyModal|DeployCaPolicyModal]] (→ `POST /api/tenants/{id}/deploy-ca`)
- **Baseline source:** [[Baseline Definitions & Mock Data]] :  `CA_BASELINE_STANDARDS` (10 rules, each with a full deployment template)

Part of [[Clarity365 MOC]]. See also [[Fleet Baseline Rollout]] and [[Fleet Baseline Drift]] for the cross-tenant versions of this same CA01 to CA10 logic.

**Known-fixed bug class:** `matchCaBaselineCode`/`validateCaPolicyCompliance` are called twice per policy :  once at sync time in [[Core Graph Layer]] against the raw Graph response, once here (and in drift-analyzer) against the *stored* `CAPolicyRule`. Any `conditions`/`grantControls` field the graph-client mapping doesn't carry through will make a genuinely-correct live policy misclassify as "Missing"/"Misconfigured" on the second pass even though the first pass got it right. `locations`, `platforms`, `userRiskLevels`, `signInRiskLevels`, `includeRoles`, and `grantControls.authenticationStrength` were all silently dropped this way (affecting CA03/CA06/CA07/CA08/CA10 on live tenants) until fixed in [[Core Graph Layer]] :  if a new baseline code's re-validation looks wrong on a live tenant but not on mock data, check this mapping first.

**A second instance of the same bug class, for Entra P2 detection this time:** `ConditionalAccessModule.tsx`'s `hasEntraP2` (used for the CA06/CA07 "requires Entra P2" badge and to gate `DeployCaPolicyModal`) used to be its own inline check, duplicated a third time in `drift-analyzer.ts`'s `tenantHasEntraP2`. Both checked `c.id === "cap-entra-p2"` (the mock-only id) and a name-substring match against `"entra id p2"` - but a live-synced tenant's `capabilities-mapper.ts` always produces one generic `cap-entra` id (P1 vs P2 distinguished only by its `tier` field), and the real generated name is `"Microsoft Entra ID P1/P2"`, which does **not** contain `"entra id p2"` as a contiguous substring (the `"1/"` sits in between) - so neither check ever matched a live tenant, regardless of actual licensing. Found via a real live tenant (Ashton John's Private School, licensed for P2 via a standalone `AAD_PREMIUM_P2_FACULTY` EDU add-on, not a bundled A5 suite) whose stored capability data already correctly showed `cap-entra` licensed with tier `"Plan 2 (P2)"`, yet the CA module still warned "no Entra P2." Consolidated into the one shared, tested `hasEntraP2Capability()` in `src/lib/utils/entra-p2.ts` - `drift-analyzer.ts`'s `tenantHasEntraP2` (still exported, since `compliance-evaluator.ts` and `FleetBaselineRolloutModule.tsx` import it by that name) now just delegates to it, so there's exactly one place left to get this right.

**Correction (2026-09-17): CA05's target app ID was wrong for this entire investigation and has been fixed.** Everything below this note previously targeted GUID `797f3427-79cd-4827-8132-47d473d450e4`, believed at the time to be "Windows Azure Service Management API"/"Microsoft Azure Management." That GUID does not correspond to any real Microsoft Azure Management service principal - it was never resolvable in any tenant, which is exactly why every earlier "ServicePrincipalNotFound" investigation below kept failing to find a fix: the ID itself was the bug, not the provisioning story built up around it. The correct, Microsoft-documented app for this baseline ("Microsoft Azure Management," covering Azure Portal, Azure CLI, Azure PowerShell, and ARM sign-in - the same app the Entra CA template picker lists, sometimes surfaced as "Azure Resource Manager" in the portal) is:
```
797f4846-ba00-4fd7-ba43-dac1f8f63013
```
Confirmed by the user directly. This app's service principal is provisioned by default in effectively every tenant (it's how Azure sign-in itself works), so the `ServicePrincipalNotFound` failure mode below should now be rare in practice rather than the norm. Fixed everywhere the old GUID appeared: `ca-baseline-matcher.ts` (`AZURE_MANAGEMENT_APP_ID`), `baseline-definitions.ts` (CA05's `targetScope` string and PowerShell template), `graph-client.ts` (CA05's deploy payload and error-message text), `drift-analyzer.ts`/`fleet-operations.ts`/`tenant-store.ts` (the "Azure Management" special-case in the realignment/deploy scoping ternary), and `mock-tenants.ts`'s CA05 fixtures.

**CA05 still needs an extra permission the others don't:** every baseline policy but CA05 targets `applications: { includeApplications: ["All"] }`. CA05 ("Require MFA for Azure management") instead references a specific application (Microsoft Azure Management) by ID - and Microsoft Graph requires the calling app registration to be able to read/resolve that application object to create a policy referencing it, meaning `Application.Read.All` is needed *in addition to* `Policy.ReadWrite.ConditionalAccess` to auto-deploy CA05 specifically. This was invisible until a deploy attempt failed with Graph's own raw error text, and remains true regardless of which appId is targeted.

**No longer its own separate checked permission.** `Application.Read.All` briefly had its own row in the Permissions report, but per explicit user feedback against having "so many separate permissions and texts when it is not needed" for one edge case out of ten baselines, it was folded into `Policy.ReadWrite.ConditionalAccess`'s own description as a one-sentence caveat instead (see [[Core Graph Layer]]), and `AddTenantModal.tsx`'s setup guidance merged the same way. The actual moment this matters - a CA05 deploy attempt - is where it's surfaced now: `deployConditionalAccessPolicy()` rewrites Graph's raw 403/`Authorization_RequestDenied` response into the specific fix when it detects this is CA05, rather than listing the permission proactively in every tenant's report.

**If CA05 ever fails with `ServicePrincipalNotFound` against the corrected appId:** this is not fixable in code (the app can't and shouldn't silently provision an Entra service principal on the tenant's behalf). The fix is Microsoft Graph PowerShell's `New-MgServicePrincipal`, which creates a service principal *from* an existing Microsoft-owned multi-tenant application's appId (no new app registration involved):
```powershell
Connect-MgGraph -Scopes "Application.ReadWrite.All"
New-MgServicePrincipal -AppId "797f4846-ba00-4fd7-ba43-dac1f8f63013"
```
Needs `Application.ReadWrite.All` or `Directory.ReadWrite.All` on the admin's own delegated sign-in - deliberately not a permission Clarity365's own app registration should ever request just for this, so it's surfaced as a one-time copy-pasteable script (same convention as every other PowerShell fallback in this app) rather than an in-app auto-fix. `deployConditionalAccessPolicy()` in `graph-client.ts` surfaces this exact command in the error message for CA05's `ServicePrincipalNotFound` failure.

**CA04 (MFA for guests) showed as Misconfigured for a genuinely correct, live-enforced policy - a real Graph schema change silently broke `targetsGuests()` (2026-09-18, live user report on dmafrica):** Deploying CA04 sends the deprecated plain string `includeUsers: ["GuestsOrExternalUsers"]` (`graph-client.ts`). Microsoft Graph still silently accepts and auto-upgrades that on create, but confirmed live - a direct GET of the resulting policy - `includeUsers` comes back empty and the real condition lives in a separate structured field, `conditions.users.includeGuestsOrExternalUsers` (`{ guestOrExternalUserTypes, externalTenants }`), which existed in neither `ca-baseline-matcher.ts`'s `RawGraphCaPolicy` type nor its `targetsGuests()` check. Two independent consequences of the same gap, both traced to the identical root cause: (1) `graph-client.ts`'s read-side mapping built `conditions.users.include` from `includeUsers || includeRoles || []`, and since Graph now always returns `includeUsers: []` for a guest policy, the persisted `CAPolicyRule` had no guest-targeting evidence left in it at all; (2) `classifyPolicyBaselineCode()`/`matchCaBaselineCode()`, run directly against the *raw* Graph response at sync time (not the mapped shape), hit the exact same blind spot in `targetsGuests()` and returned `null` instead of `"CA04"`. `validateCaPolicyCompliance()`'s overall `isValid` requires `matched === codeUpper` in addition to the per-code checks passing, so a `null` match forced `isValid: false` regardless of the policy's CA04-specific check (mfa granted, correct name) passing on its own - which is why the policy landed in `misconfiguredMap` (name-regex fallback finds "CA04" in the display name, but `validateCaPolicyCompliance` then fails it) instead of `baselineMap`. Fixed at both points: `targetsGuests()` now checks `includeGuestsOrExternalUsers` directly (fixes the raw-response classification), and the read-mapping re-encodes a present `includeGuestsOrExternalUsers`/`excludeGuestsOrExternalUsers` as the same `"GuestsOrExternalUsers"` marker string in `include`/`exclude` the matcher already looked for (fixes re-validation against the persisted shape) - no matcher change needed for that second path. Verified against dmafrica's real policy data directly (not guessed): confirmed `matchCaBaselineCode`/`classifyPolicyBaselineCode`/`validateCaPolicyCompliance` all now resolve correctly for both the raw-Graph shape and the previously-broken persisted shape. The Microsoft-side policy itself was correct and enforcing the whole time - only Clarity365's own re-validation was wrong; existing tenants need one fresh sync to pick up the corrected mapping. CA02 uses the same deprecated `excludeUsers: ["GuestsOrExternalUsers"]` convention for its own guest exclusion and benefits from the same fix, though CA02's own `validateCaPolicyCompliance` branch doesn't check guest exclusion so it wasn't independently exhibiting this bug's symptom.

**Follow-up (2026-09-18, same day): the mapping function that produced this bug had zero test coverage of its own - fixed as part of a full code+vault review.** The inline `.map()` callback inside `fetchLiveTenantSnapshot` that builds each `CAPolicyRule` was extracted into its own exported, named function, `mapConditionalAccessPolicy()` (in `graph-client.ts`, same "pull the mapping step out so it's testable without a live Graph response driving it" convention as `secure-score-mapper.ts`). Only the pure `ca-baseline-matcher.ts` functions it calls were ever tested in isolation - the actual mapping step feeding them real Graph data had none, which is exactly where today's CA04 bug lived undetected. Added 4 tests in `graph-client.test.ts` covering: the real dmafrica CA04 shape (regression test for the exact bug above), a CA03 admin-role policy (confirms role GUIDs don't leak into `conditions.users.include` - see the next paragraph), platforms/locations/risk-level passthrough (CA06/CA07/CA08), and the null/no-match fallback for a custom policy. Also fixed in the same pass: `include: [...(includeUsers || includeRoles || [])]` was dead code - Graph always returns `includeUsers` as an array (empty, never omitted), which is truthy in JS, so the `|| includeRoles` branch could never fire; `includeRoles` was already correctly preserved on its own separate field and read from there by `targetsAdminRoles()`, so nothing was actually broken, but the fallback was misleading and shared the exact "empty array can mask a real value" shape as the CA04 bug itself. Simplified to `includeUsers || []`.

**CA01 used an invalid Graph enum value and could never actually deploy to a live tenant:** CA01's `conditions.clientAppTypes` was `["exchangeActiveSync", "otherClients"]` everywhere it appeared (the live deploy payload in `graph-client.ts`, both PowerShell script templates in `baseline-definitions.ts`/`remediation-generator.ts`, `ca-baseline-matcher.ts`'s `LEGACY_CLIENT_APP_TYPES`, the mock CA01 fixture in `mock-tenants.ts`, and the local snapshot-realignment payloads in `drift-analyzer.ts`/`fleet-operations.ts`/`tenant-store.ts`). `"otherClients"` is not a real Graph `conditionalAccessClientApp` enum member - the actual value is `"other"` (confirmed against Microsoft's own enum reference). Because every occurrence agreed with every other, this was invisible in mock/demo data and in the compliance re-check (`.some()` still matched on the co-present `"exchangeActiveSync"` value) - it only surfaced as a hard failure the moment an actual live deploy hit real Microsoft Graph, which rejects the whole policy object with error `1007: Incoming ConditionalAccessPolicy object is null or does not match the schema of ConditionalAccessPolicy type` rather than just dropping the bad array entry. Found live on Ashton John's Private School; confirmed fixed by re-deploying to that same tenant afterward and reading the resulting policy back out of Graph. Fixed in all nine locations at once - a good example of the "same wrong value copy-pasted everywhere, so it never disagreed with itself" variant of this vault's recurring duplicated-logic bug class (see [[Optimization Plan]] item 7), distinct from the usual "one copy drifted from another" variant.

**CA08 changed to a country allow list (2026-10-05).** The old CA08 excluded only trusted locations, so it would block every home and mobile sign-in on the 9 of 10 tenants without trusted locations. Deploying CA08 now asks for the allowed countries in `DeployCaPolicyModal`, pre-filled with the tenant's most common sign-in country. It first creates a "CA08: Allowed countries" named location, then the report-only policy that excludes it. If the policy step fails, the location is removed again. See [[Optimization Plan]] and [[Core Graph Layer]].
