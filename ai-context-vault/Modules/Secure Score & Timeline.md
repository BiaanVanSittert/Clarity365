# Secure Score & Timeline

Microsoft Secure Score card with 30/90-day deltas, benchmark comparison, a historical trajectory, and a clickable per-control table (2026-09-17: extended from a read-only list into a full detail-drawer + auto-deploy UI - see below).

- **Component:** `SecureScoreModule.tsx`, `SecureScoreControlDrawer.tsx` (in `modals/`)
- **Reads:** `TenantSecuritySnapshot.secureScore` (prop-driven)
- **Key types:** `TenantSecureScore`, `SecureScoreControl`, `SecureScoreControlDeployment` :  see [[Domain Types]]
- **Renders:** `StatusPill`, `EmptyStateRow`, `useTheme`, `Drawer`, `DeployCaPolicyModal` (reused, not reimplemented)
- **Data origin:** [[Data Mappers]] (`secure-score-mapper`), populated via [[Core Graph Layer]]
- **Exposed to agents via:** [[MCP Server]] `get_tenant_secure_score` tool

## 2026-09-17 extension: full control detail + Auto/Guided/Manual deploy

Triggered by a client-supplied Excel export of Microsoft's own Secure Score "recommended actions" (Rank/action name/0-1 flag/score-impact %/category/product - a temporary file, not committed, used only to cross-check the live control catalog and then deleted). The Excel didn't have absolute points, full descriptions, or user-impact ratings - those already existed live via `secureScoreControlProfiles`; the real gaps were on the app side. Built in phases:

**Phase 1 - data model.** Added to `SecureScoreControl`: `description` (the tenant-facing "why this matters" text, from `secureScores.controlScores[].description` - distinct from `remediationSummary`'s "how to fix" steps, which come from the separate `secureScoreControlProfiles` catalog joined by id), `actionUrl` (Graph's `controlProfile.actionUrl` - a real deep link straight to the exact admin portal blade), `remediationImpact`, `threats`, `implementationStatus`, and `deployment: SecureScoreControlDeployment` (`{ type: "auto"|"guided"|"manual_only", clarity365Action? }`).

**Live-verified bug fixed in the same pass:** `userImpact`/`implementationCost` were being silently collapsed to `"Moderate"` for anything Graph didn't classify as low/moderate/high. A real pull against Coetzee Architects showed **`"Unknown"` is Graph's own value for ~70% of all controls** (338 of ~460 profiles), plus a separate `"Medium"` spelling neither the old type nor the old normalizer handled. Fixed by adding `"Unknown"` to the type union, treating `"Medium"` as an alias of `"Moderate"`, and defaulting truly unrecognized/missing values to `"Unknown"` rather than a guessed severity (see `normalizeCostOrImpact` in `secure-score-mapper.ts`). Confirmed live in the browser afterward: a dozen real Coetzee controls now correctly show "Unknown" instead of the old, misleading "Moderate".

**Phase 2 - `secure-score-control-mapping.ts`.** A deliberately short, live-verified allowlist mapping a Secure Score `controlName` to a Clarity365 baseline code: `BlockLegacyAuthentication`→CA01, `MFARegistrationV2`→CA02, `AdminMFAV2`→CA03, `SigninRiskPolicy`→CA06, `UserRiskPolicy`→CA07 (confirmed against Coetzee's real `secureScoreControlProfiles` catalog). Deliberately excludes EDR/AV/ASR/BitLocker and CA04/CA05/CA08/CA09/CA10: the Device-category controls (`scid_2000`, `scid_2010`, `scid_2090`, etc.) score actual per-device telemetry, not "does this Settings Catalog policy exist" - deploying the matching Clarity365 policy should move those scores over time, but it isn't the same deterministic check CA baselines get, so those controls stay "guided" rather than "auto" until proven otherwise live. Same "never guess Graph behavior" discipline as the CA05 appId correction and the disproven templateId theory - see [[Conditional Access Policy Scanner]].

**Phase 3 - `SecureScoreControlDrawer.tsx`.** Clicking any table row opens a detail drawer: points/status/user-impact/cost summary, "Why This Matters" (+ threat chips), "How To Fix" (Graph's own remediation steps, converted from HTML to plain text - see below - plus the `actionUrl` link and any `powershellCommand`), and a deployment action panel that's one of: an **Auto-Deploy** button (only for controls whose `clarity365Action` matches a real `CA_BASELINE_STANDARDS` code - it opens the *existing* `DeployCaPolicyModal` unmodified, so it inherits that modal's already-live-tested Report-Only-mode deploy flow rather than a second, parallel implementation), a **"managed elsewhere"** panel with a jump-to-Endpoint-Security button for the non-CA `deployment.type === "auto"` case, or plain **guided/manual** text otherwise. The table itself also grew a compact Auto/Guided/Manual badge column so a security engineer can prioritize without opening every row.

**`src/lib/utils/html-to-text.ts` (`htmlToPlainText`).** Graph's `remediation`/`remediationImpact` fields are real HTML (`<ol>`/`<li>`, `<em>`, smart-quote entities like `&ldquo;`/`&rdquo;`, confirmed live). JSX text interpolation never renders markup - it escapes it - so without this, remediation steps showed up on screen as literal `<ol> <li>...` text. Deliberately plain-text conversion rather than `dangerouslySetInnerHTML`, to avoid needing a sanitizer for content this app doesn't author.

**Phase 4.** The header's "Generate Remediation Script" button used to call `onOpenRemediation("all")`, running `remediation-generator.ts` - a generator with zero awareness of individual Secure Score controls (it only ever covered CA/forwarding/MFA/orphaned-accounts/SharePoint-sharing/unprotected-admins as its own hardcoded findings). Clicking it here produced plans unrelated to anything in this table. Replaced with "Fix Top Priority Action", which opens the new drawer directly on the highest score-gap open control - real, Secure-Score-specific guidance instead of a mismatched generic plan. `onOpenRemediation` was consequently dropped from this module's props entirely (dead after the swap) - `AppShell.tsx` now passes `onRefresh`/`onNavigate` instead, matching [[Conditional Access Policy Scanner]]'s existing prop contract for the same purpose.

**Backward-compatibility gotcha found live, fixed defensively:** `TenantSecuritySnapshot` is persisted to disk as-is with no migration step (see [[Domain Types]]'s note on it being a god object). Loading a tenant synced before this change crashed the whole module on `ctrl.deployment.type` (undefined) - live-reproduced on Coetzee Architects before a fresh sync. Fixed with a `withLegacyDefaults()` normalizer at the top of `SecureScoreModule.tsx` that backfills `description`/`deployment` for any control missing them, independent of whether/when that tenant re-syncs. Worth remembering for the *next* new required field added to `SecureScoreControl` (or any other hub-type array element) - this codebase has no formal schema-migration system, so a defensive UI-side default is the standing pattern, not a one-off.

## 2026-09-17, later same day: curated "where to go" guidance for weak remediation text

User feedback: some controls' "How To Fix" text names a setting but never says which admin portal to visit. Live-audited against Coetzee Architects' real synced snapshot to size and ground the fix rather than guessing: **22 of 41 currently-open (Unresolved/Partial) controls (54%) name a setting with zero navigation guidance** - e.g. `mdo_allowedsenderscombined`: *"Remove all allowed domains and allowed senders from all your inbound anti-spam policies"*, never mentioning the Defender portal at all. Nearly all 22 cluster onto a handful of real destinations: 18 are Defender for Office 365 anti-spam/anti-phishing/anti-malware/Safe Attachments policy settings (all under the Microsoft Defender Portal's Email & collaboration → Policies & rules → Threat policies area), 3 are Microsoft Purview Information Protection settings, and 3 (`exo_mailtipsenabled`, `exo_mailboxaudit`, `exo_storageproviderrestricted`) have no GUI at all - PowerShell-only via `Connect-ExchangeOnline`, which Graph's own text already gives the command for but never names the admin center it's opened from.

Added `src/lib/data/secure-score-remediation-guides.ts`: a small, deliberately scoped `Record<controlName, { portalName, url, navPath[] }>`, built from a handful of shared portal-template constants (`MDO_ANTI_PHISHING`, `MDO_ANTI_SPAM_INBOUND`, `MDO_ANTI_MALWARE`, `MDO_SAFE_ATTACHMENTS`, `MDO_SAFE_ATTACHMENTS_GLOBAL`, `PURVIEW_LABEL_POLICIES`, `PURVIEW_AUTO_LABELING`, `PURVIEW_DATA_MAP`, `EXO_POWERSHELL_ONLY`) so fixing a renamed Microsoft blade later is a one-constant edit, not 18. `SecureScoreControlDrawer.tsx`'s "How To Fix" section renders this as a "Where to go: ..." breadcrumb block *above* Graph's own remediation text when a guide exists for that control id - Graph's text still supplies the "what to set," this only adds the missing "where." The existing "Open in Microsoft Admin Center" link keeps using `control.actionUrl` when Graph provides one; the guide's own `url` is only used as the link target when `actionUrl` is absent (true for all 22, confirmed live).

Deliberately scoped to controls found weak on a live audit, not Microsoft's entire ~460-control catalog - extend this map incrementally as new gaps are spotted on other tenants, the same way `baseline-definitions.ts`'s CA PowerShell templates grew one baseline at a time rather than all at once.

## 2026-09-17, third pass: "No description available" was a stale-snapshot artifact, not a real Graph gap - one genuine exception found and fixed

Follow-up request: "get a description under each." Before authoring anything, live-audited Coetzee Architects' *persisted* snapshot first - every one of its 70 controls showed the mapper's placeholder ("No description available for this control."), suggesting a large content gap. But a direct live Graph call (`secureScores?$top=100`, same query `fetchLiveTenantSnapshot` uses) showed the actual latest secureScores entry (`createdDateTime: 2026-09-17`) has real Microsoft-authored descriptions on 69 of 70 `controlScores[]` entries - an *older* entry in the same batch (`2026-06-20`) had zero. The persisted snapshot was simply stale (same root cause as the `deployment`-field crash documented above - no snapshot migration, and in this case no *recent enough* sync either), not a mapper bug or a Microsoft-side gap. Confirmed by forcing a real "Sync Tenant" and re-checking the DB directly: missing-description count dropped from 70/70 to 1/70 immediately, no code change involved. The same staleness was confirmed on two other tenants' un-refreshed snapshots (71/71 and 202/202 missing) - this is a demo-environment freshness issue, not something specific to Coetzee.

The one control confirmed live to have a genuinely blank `description` from Microsoft itself: `mdo_autoforwardingmode`. Added `src/lib/data/secure-score-description-fallbacks.ts` - deliberately a one-entry map today, checked by `mapSecureScoreControl()` only when Graph's own `scoreEntry.description` is empty, same "extend only when live-confirmed" discipline as `secure-score-remediation-guides.ts`. Resist the urge to pre-fill this for every control that currently shows the placeholder in a demo tenant - check whether that tenant has actually been synced recently first, the same check that unwound most of this investigation.

## 2026-09-19: first non-Microsoft-catalog control - company sign-in page branding

User request: add company branding as a recommendation. Checked live first rather than assuming - Microsoft's Secure Score catalog has **no** control for this at all (confirmed against all ~462 real `secureScoreControlProfiles` entries). So this is Clarity365's own recommendation, not something pulled from Graph's scoring - the first control in this table that isn't Microsoft-sourced. Built live-checked rather than a static decoration, since Graph does expose a real, checkable signal: `organization/{tenantId}/branding/localizations` (confirmed live against Coetzee Architects, which already has a real logo configured there) - and it needs no new permission grant, since it reuses `Organization.Read.All`, already required for tenant capability detection.

`src/lib/services/company-branding-analyzer.ts` - `buildCompanyBrandingControl()`, a pure function (tested) that inspects the localizations response for any set `bannerLogoRelativeUrl`/`squareLogoRelativeUrl`/`backgroundImageRelativeUrl` and returns `"Completed"` or `"Unresolved"` accordingly. `scoreCurrent`/`scoreMax` fixed at `0/0` so it never affects the real Microsoft attainment percentage (which comes straight from Graph's own `currentScore`/`maxScore`, not a sum over this array, but 0/0 keeps the intent explicit regardless). `deployment.type: "guided"`, not `"auto"` - setting a real logo needs an uploaded image file, not something a one-click deploy can do. `actionUrl` deliberately points at the Entra admin center's top-level URL rather than a deep-link fragment to the exact Company Branding blade - that exact fragment path hasn't been verified live, and a wrong one silently redirects to the portal root anyway, so the extra precision wasn't worth claiming.

Wired into `fetchLiveTenantSnapshot`'s existing Secure Score sync step in `graph-client.ts`, appended to `controls` after the Microsoft-sourced ones, inside its own `try` so a failure fetching branding data can't take down the other 70+ real controls. Verified end-to-end against Coetzee's real live data (not just the pure function's unit tests) - correctly returned `"Completed"` given that tenant's actual configured logo.

## 2026-09-22: authored Device-control guides (protects / user impact / how-to-fix) - first of two planned groups

User request: a guide per Device-category Secure Score recommendation covering what it protects, possible user impact, and the guide/PowerShell to implement it. Live-audited first rather than assuming scope: pulled every distinct Device-category control across the three tenants that actually have them (Axiomatic Consultants, dmafrica, Zubat Nine - Crimson Line has zero, no Intune enrollment) - **131 distinct controls**, not "a handful." Broke into four real sub-domains and sequenced with the user rather than guessing: (1) the 19 Attack Surface Reduction rules - already fully covered by the existing [[Attack Surface Reduction Rules]] module, nothing new needed; (2) Defender AV/EDR/Firewall/SmartScreen (31 controls); (3) BitLocker/TPM/Secure Boot/Credential Guard/VBS/LAPS (13 controls); (4) ~70-80 Windows local security policy hardening controls (password policy, SMB/NTLM/LDAP signing, UAC, etc.) - zero existing Clarity365 infrastructure in this domain, a separate, larger follow-up. User chose to start with groups 2+3 (44 controls total, "closest to what Clarity365 already deploys").

**Confirmed live before authoring anything:** all 44 controls return `userImpact`, `remediationImpact`, and `implementationCost` as the *literal string* `"Unknown"` from Graph - not a placeholder-detection bug this time (unlike the stale-snapshot case above), genuinely Microsoft's own value on a freshly-synced snapshot. `remediationSummary` is also the same generic "go check Vulnerability Management > Recommendations, choose remediation or exception options" boilerplate for all 44, unlike MDO's per-policy summaries. `description` is the one field that's genuinely good (real, specific) for nearly all of them, so it's left alone. `powershellCommand`/`threats` are 0% populated, same as the rest of the Device category.

Added `src/lib/data/device-secure-score-guides.ts` - `DEVICE_CONTROL_GUIDES: Record<controlId, DeviceControlGuide>`, one entry per control with an authored `userImpact`, a `mechanism` tag (`clarity365_defender_av`/`clarity365_edr`/`clarity365_bitlocker` for the handful that map 1:1 to a toggle Clarity365 already deploys; `intune_settings_catalog`/`intune_firewall`/`intune_account_protection` for real Microsoft mechanisms Clarity365 doesn't deploy yet; `mde_diagnostic` for sensor-health signals with no single policy fix; `hardware_firmware` for TPM/Secure Boot/BitLocker-compatibility state that no Graph/Intune policy can flip remotely; `defender_portal_tenant_wide` for Tamper Protection/EDR block mode, which are Defender-portal toggles, not device policy), a verified `powershellCommand` only where Microsoft documents a real one (deliberately omitted for Tamper Protection - enabling it is specifically what blocks local PowerShell changes, so offering one would be self-defeating - and for TPM/Secure Boot, which are firmware state), and `sourceUrls` for every mechanism claim (Microsoft Learn's Account Protection/Disk Encryption/Firewall settings references, `Set-MpPreference` docs, Windows LAPS deployment docs - fetched and read during authoring, not asserted from memory, same discipline as the DLP catalog).

`SecureScoreControlDrawer.tsx` now layers this in without touching `deployment.type` (Device controls deliberately stay `"guided"`, per the existing per-device-telemetry rationale in `secure-score-control-mapping.ts` - a native toggle existing doesn't make the *Secure Score check itself* deterministic): a new "User Impact" section renders `deviceGuide.userImpact` only when `control.userImpact === "Unknown"`; the "Where to go" box now also renders from `deviceGuide.portal` when the older MDO/EXO/MIP `guide` map has no entry; an amber "Clarity365 already has this" callout appears when `deviceGuide.clarity365Action` names an existing toggle (e.g. BitLocker's `requireDeviceEncryption`); the PowerShell block now falls back to `deviceGuide.powershellCommand` when Graph's own field is empty, with `deviceGuide.powershellCaveat` shown underneath (most are explicitly flagged "for one unmanaged/test machine only - the Intune policy is the real fix for a fleet," since a raw `Set-MpPreference` run against one box doesn't survive an Intune-managed device's next policy sync). Verified live in the browser against Axiomatic (not just `tsc`/tests): `scid_2003` (Tamper Protection) correctly shows the authored user-impact/caveats with no PowerShell block; `scid_2090` (BitLocker encryption) correctly shows the "Clarity365 already has this" callout pointing at the BitLocker Policy toggle. `tsc` clean, 568 tests still passing (no new automated tests - this is presentational/content, same as the remediation-guides and description-fallbacks maps above).

Two flagged lower-confidence entries, called out in their own `caveats` rather than presented with false confidence: `scid_6100`/`scid_6101` (WSL Defender plugin / WSL kernel hardening - newer, more niche controls whose exact current setup steps should be re-verified before a standard baseline), and `scid_102` (Windows 11 22H2+ LSA protection - very likely satisfied by the same Settings Catalog setting as `scid_25`'s legacy LSA protection, but that exact scoring boundary wasn't independently confirmed live in this pass).

## 2026-09-22, same day: group 3 - the remaining 69 Windows local security policy controls, completing the Device category

User confirmed "proceed with the next" straight after group 2 shipped - continued directly rather than re-scoping. This is the group flagged as the largest (69 controls, confirmed by exact count against the same 131-control live pull, not the earlier ~70-80 estimate) and the one with **zero pre-existing Clarity365 module to lean on** - every mechanism here is a genuinely new admin path for this app: password/account lockout policy (Device Lock CSP), UAC/elevation, SMB/NTLM/LDAP hardening, RDP/WinRM/Remote Assistance, Netlogon secure channel (domain-joined only - explicitly flagged as no-op on Entra-only cloud-native devices, since that distinction matters for an MSP fleet that's frequently cloud-native), network/ICS/IP-routing hardening, local/built-in account hardening, service-account hardening (the one sub-group that's genuinely per-instance detection, not a single policy - `scid_3001`/`scid_3002`/`scid_3003`, unquoted service paths/insecure service locations/cached service-account passwords - framed as an Intune Proactive Remediation detect+remediate pair rather than a one-time fix, since new software installs can reintroduce the same issue), AutoPlay/AutoRun, Chrome/Adobe browser policy (flagged where it needs a vendor ADMX import into Intune first, not natively in Settings Catalog), and a standalone control (`scid_107`, blocking mshta.exe's outbound network access) confirmed via live search to be a genuinely new (early 2026) Secure Score recommendation implemented as an Intune Firewall Rules per-app block - not one of the existing 19 ASR rules, despite living in the same "living-off-the-land technique" threat family.

Same file (`device-secure-score-guides.ts`), same `DEVICE_CONTROL_GUIDES` map, same `getDeviceControlGuide()` lookup - no drawer changes needed this time, since `SecureScoreControlDrawer.tsx` already looks up by `control.id` generically regardless of which group a control belongs to. Research followed the same per-mechanism-family pattern as group 2 (Intune's Device Lock/Local Policies Security Options/Remote Desktop Services/WinRM/AutoPlay Settings Catalog references, Chrome Enterprise policy docs, Adobe's community ADMX project, and a live search confirming `scid_107`'s actual novelty and mechanism), not per-control - genuinely distinct settings within the same family share one verified mechanism.

**A real gap caught before it shipped, not after:** a manual count-and-diff of the authored entries against the full expected 113-control ID list (44 from group 2 + 69 from group 3) came up one short - `scid_64` ("Restrict anonymous access to named pipes and Shares") had been omitted while drafting the SMB/NTLM group. Caught by generating the full expected ID list from the original live pull and diffing it against the file's actual keys, rather than trusting the drafted content was complete - added afterward, `tsc` re-confirmed clean, and the diff re-run to confirm 113/113 present with no duplicate keys. Worth remembering as the check to run again if this map is ever extended further: don't trust a large hand-authored batch's completeness without diffing it against the original live-sourced ID list.

Verified live in the browser (not just `tsc`/tests) against Axiomatic: `scid_3001` (the one entry with a genuinely complex regex-based PowerShell command, the highest risk of a shipped string that breaks the code block or the copy button) renders and copies cleanly, no console errors. `tsc` clean, 568 tests still passing (same as group 2 - no new automated tests, this is authored content).

**Device Secure Score guide catalog is now complete** (113 of 131 Device-category controls - the remaining 18 are the existing Attack Surface Reduction rules, deliberately not duplicated since [[Attack Surface Reduction Rules]] already covers them). No further groups pending from the original scoping conversation.
