# Attack Surface Reduction Rules

Reports the state of all 19 real Microsoft Defender ASR rules for the tenant, colored by a 4-tier traffic light (Critical/Gap/In Progress/Protected), grouped the same way Microsoft's own docs group them (3 "Standard Protection" rules, then 16 "Other" rules). Click a rule for its full description, risk mitigated, per-rule caveats (no Warn mode / no Advanced Hunting telemetry), and setup guidance.

- **Component:** `AsrRulesModule.tsx`
- **Reads:** `TenantSecuritySnapshot.asrRules`, gated on `hasDefenderForEndpointCapability()` (`src/lib/utils/defender-for-endpoint.ts`) - a tenant with no Defender for Endpoint/Defender for Business capability sees a plain "requires Defender for Endpoint" banner instead of a wall of red for something it can't configure.
- **Key types:** `AsrRuleMode`, `AsrRuleState { ruleId, mode, sourcePolicyNames?, hasConflict? }` :  see [[Domain Types]]
- **Static catalog:** `src/lib/data/asr-rule-definitions.ts` :  `ASR_RULE_DEFINITIONS`, the 19 real rules (GUID, description, risk mitigated, category, Warn-mode/telemetry support, manual setup guidance), verified against Microsoft Learn's ASR rules reference.
- **Classifier:** `src/lib/services/asr-rule-matcher.ts` :  `classifyAsrRuleTier()` (has a test). A fresh 4-state enum (`critical`/`gap`/`in_progress`/`protected`), not a reuse of `MfaRiskTier` - this is rule configuration status, not user risk, and the states genuinely differ. Critical is reserved for a Standard Protection rule sitting at Not Configured.
- **Renders:** `Drawer` (same click-a-row-for-detail pattern as [[Intune Endpoint Security]] and [[Sign-In Logs & CA Diagnostics]]).
- **Server-only rule exclusion:** "Block Webshell creation for Servers" (the one rule with no Advanced Hunting telemetry at all, and only applicable to on-prem/hybrid Exchange servers) is excluded from the tier counts and the sidebar badge, tagged "Server Only" in the list instead - a pure-cloud tenant shouldn't see an inflated gap count for something it has no way to act on.
- **Sidebar badge:** `asrRuleGapCount` in `Sidebar.tsx`, computed the same way (via `classifyAsrRuleTier`, excluding the server-only rule) rather than re-deriving its own logic, and gated on the same `hasDefenderForEndpointCapability()` check as the module itself so an unlicensed tenant's nav doesn't show a misleading count.
- **MDE capability detection:** `hasDefenderForEndpointCapability(snapshot)` (`src/lib/utils/defender-for-endpoint.ts`) is the single shared gate used by both the module and the sidebar badge. It matches capability id `cap-mde` (the generic id a live-synced tenant's `capabilities-mapper.ts` always produces) as well as the mock-only `cap-mde-p1`/`cap-mde-p2` ids, plus a name-substring fallback, plus a tenant-tier fallback (`M365_E5`/`M365_BP`) for tenants with no matching capability entry at all - same defense-in-depth pattern as `ConditionalAccessModule.tsx`'s Entra P2 check. This was added after a live bug report: Business Premium tenants genuinely include Defender for Business (the SMB-scoped equivalent of Defender for Endpoint), but `capabilities-mapper.ts`'s `hasMde` SKU list didn't recognize the `SPB` skuPartNumber, and this module's own gate only ever checked the mock-only ids - so the ASR tab silently disappeared for every real Business Premium tenant regardless of licensing. Both root causes are fixed; see [[Domain Types]] for where `cap-mde` fits among the other capability ids.
- **Detection activity (Phase 2):** on mount, the module POSTs to `/api/tenants/[id]/asr-detections` (empty body) for a per-rule 30-day hit summary, rendered as a small `N events (30d)` badge next to the mode badge - deliberately not tier-colored, so a Block rule catching something reads as the system working, not a fault. Opening a rule's drawer POSTs again with `{ ruleId }` for that rule's raw recent events (cached per rule for the session), each expandable inline to show parsed `additionalFields`.

## Data flow for configuration state

Originally, "Phase 1" only ever shipped the UI/tiering/mock-data half of configuration-state reporting - there was no code anywhere that fetched real ASR rule configuration from a live tenant, so every live sync left `asrRules` `undefined` and every rule silently defaulted to Not Configured regardless of the tenant's actual state (a live bug report: "a client has business premium... but the ASR rule does not show" turned out to be this, not the MDE capability detection issue described above (both were real, independent bugs found back to back). This is now fixed - live tenants get real configuration data.

- **Three independent, mergeable Intune surfaces**, verified against Microsoft Learn and an official Microsoft GitHub sample (not guessed), since a real tenant can use any of them and Intune merges all that apply into one superset per device:
  1. **Settings Catalog** (`Endpoint security > Attack surface reduction policy`, the modern format Microsoft's own docs say most tenants use today) :  `deviceManagement/configurationPolicies` filtered by `templateReference/templateFamily eq 'endpointSecurityAttackSurfaceReduction'`, then each policy's `/settings`. Rules are keyed by a human-readable slug in each setting's id (e.g. `..._blockexecutionofpotentiallyobfuscatedscripts_block`), not the GUID - the slug<->rule-GUID map is built at sync time from Microsoft's own tenant-agnostic catalog metadata (`deviceManagement/configurationSettings?$filter=rootDefinitionId eq '...'`, cached process-wide on `globalThis` the same way the Graph token is, since it's global Microsoft data, not per-tenant) cross-matched against `ASR_RULE_DEFINITIONS`' verified names, rather than 19 hand-typed guesses.
  2. **Legacy classic Device Configuration profile** (`Endpoint protection` profile, `windows10EndpointProtectionConfiguration`) :  simplest surface, each rule is a flat named top-level property (e.g. `defenderOfficeAppsLaunchChildProcessType`). Only 15 of the 19 catalog rules are expressible in this older schema (a Microsoft-side gap, not this app's) - see `LEGACY_ASR_PROPERTY_TO_RULE_ID` for the exact, verified allowlist. Deliberately NOT a generic `defender*Type` name match: `defenderNetworkProtectionType`/`defenderGuardMyFoldersType` match that naming pattern but are Network Protection/Controlled Folder Access, unrelated Defender features.
  3. **Older "Endpoint Security Templates" intents** (being phased out but not retired) :  same 15-rule schema as #2, reached via `deviceManagement/intents` `definitionValues` instead of a flat resource read. Reuses the intents list [[Intune Endpoint Security]] already fetches for antivirus/EDR policy counts, filtered by the same category-name-matching convention, rather than a second identical request.
- **Mapper:** `src/lib/services/asr-configuration-mapper.ts` (has a test) :  `buildAsrSlugMap()` (surface 1's slug<->GUID resolution), `mapAsrSettingDefinitionIdsToSignals()` (surface 1), `mapNamedPropertyValuesToSignals()` (shared by surfaces 2 and 3), and `mergeAsrRuleStates()` - the single cross-surface merge point every signal funnels through, always returning exactly 19 entries.
- **Conflict handling:** per Microsoft's documented ASR policy merge behavior, when two+ sources set a rule to *different* modes, the conflicting setting is dropped entirely rather than one source winning - so the effective mode is genuinely Not Configured, which is what `mergeAsrRuleStates()` returns. `AsrRuleState.hasConflict` is what keeps that distinguishable from a rule nobody has ever touched, since a self-canceling policy pair is a real, actionable misconfiguration - surfaced as a row-level badge and a drawer warning box in `AsrRulesModule.tsx`, listing every contributing `sourcePolicyNames` entry.
- **Graph calls:** `graph-client.ts`'s ASR configuration section (right after the existing Intune Endpoint Security intents fetch), one try/catch per surface, each pushing to `syncErrors` with its own `"ASR Rules (...)"`-prefixed message on failure. If every surface fails, `asrRules` is left untouched rather than overwritten with an empty result (preserves last-good data on a transient/permission failure, same guard every other optional sync section uses).
- **Sync error banner:** `AsrRulesModule.tsx` filters `snapshot.syncHealth.errors` for the `"ASR Rules"` prefix and renders it in the same rose-bordered banner style already established by [[Defender for Office 365 & TABL|MdoPoliciesModule]], since a false "Not Configured" reading here is unusually costly to trust.
- **No new admin consent needed:** `DeviceManagementConfiguration.Read.All`, already requested/tested for the existing Intune Endpoint Security permission, covers all three new endpoints.
- **Permanent limitations** (Graph can't see these, not a future TODO): ConfigMgr-managed (tenant-attach) devices, raw custom OMA-URI profiles not recognizable as the named ASR CSP path, and on-prem GPO not synced through Intune. Also, like every other policy-reporting module in this app (Conditional Access, Secure Score), this reports tenant-wide configured state, not per-device rollout - a rule assigned to only a pilot group still shows as configured tenant-wide.

## Data flow for detection activity
- **Types:** `AsrRuleActivitySummary`, `AsrDetectionEvent` :  see [[Domain Types]]. Neither is stored on `TenantSecuritySnapshot` - both are on-demand only, never part of a tenant sync.
- **Mapper:** `src/lib/services/asr-detection-mapper.ts` (has a test) :  `mapActionTypeToRule()` resolves a raw Advanced Hunting `ActionType` (e.g. `AsrRansomwareBlocked`) back to a rule + bucket via `ASR_RULE_DEFINITIONS`' `advancedHuntingActionTypes` lists; `buildActivitySummaries()` zero-fills the full 19-rule array from an aggregate query's `{ActionType: count}` shape; `synthesizeMockActivity()` generates deterministic (hashed, not random) demo numbers for mock tenants - always zero for a Not Configured rule or the no-telemetry Webshell rule, since a rule that isn't enforcing anything can't have logged a detection.
- **Graph calls:** `graph-client.ts`'s `fetchAsrDetectionSummaries`/`fetchAsrDetectionEvents`, mirroring `deployConditionalAccessPolicy`'s mock-short-circuit-first shape. Live path is `POST https://graph.microsoft.com/v1.0/security/runHuntingQuery` (v1.0, not beta) with a KQL query against `DeviceEvents`, requiring `ThreatHunting.Read.All` - a materially more restrictive permission than anything else this app requests, so a missing-permission response is treated as an expected, graceful `{ error }` outcome, not a thrown exception.
- **Orchestration:** `tenant-store.ts`'s `getAsrDetectionSummaries`/`getAsrDetectionEvents`, same decrypt-then-delegate shape as `testPermissions`/`testExoConnectivity`.
- **Permissions self-test:** `ThreatHunting.Read.All` is now tested by `testAppRegistrationPermissions` (`graph-client.ts`) - a live tenant that hasn't granted it sees this surfaced as an explicit, expected, optional gap in the Permissions modal (and in `AddTenantModal.tsx`'s setup guidance) rather than only discovering it via the module's own "Detection activity unavailable: Missing application roles..." error text, which is Microsoft Graph's own literal 403 message passed straight through. `PermissionTestResult` gained `method`/`body` (defaulting to GET) specifically to support this - `runHuntingQuery` has no GET form, so this was the one existing permission needing a POST-based self-test; the check itself runs a minimal, cheap query (`DeviceEvents | where Timestamp > ago(1d) | take 1`) rather than anything resembling the real 30-day aggregate. Marked `optional: true` (excluded from the pass/fail rollup) since ASR rule configuration reporting is fully unaffected without it - only the event-count badges and event list are unavailable.

## Scope: Phase 3 remaining
Phase 1 (config-state reporting, now including the live-tenant fetch - see above) and Phase 2 (detection activity) are both done. Still outstanding:
- **Phase 3 (not built):** the "auto-create in Audit mode" deploy action, mirroring [[Conditional Access Policy Scanner]]'s `deployBaselinePolicy`/`DeployCaPolicyModal` pattern exactly, but against Intune's `deviceManagement/intents` (Attack Surface Reduction category) rather than Conditional Access policies - noting Intune profiles need a separate assignment call, unlike a CA policy's inline scope.

Each rule's drawer already shows manual setup guidance (PowerShell + Intune portal steps) sourced from `ASR_RULE_DEFINITIONS`, so "how do I turn this on" is answered today even before the Phase 3 one-click button exists.
