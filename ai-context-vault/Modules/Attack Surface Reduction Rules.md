# Attack Surface Reduction Rules

Reports the state of all 19 real Microsoft Defender ASR rules for the tenant, colored by a 4-tier traffic light (Critical/Gap/In Progress/Protected), grouped the same way Microsoft's own docs group them (3 "Standard Protection" rules, then 16 "Other" rules). Click a rule for its full description, risk mitigated, per-rule caveats (no Warn mode / no Advanced Hunting telemetry), and setup guidance.

- **Component:** `AsrRulesModule.tsx`
- **Reads:** `TenantSecuritySnapshot.asrRules`, gated on `hasDefenderForEndpointCapability()` (`src/lib/utils/defender-for-endpoint.ts`) - a tenant with no Defender for Endpoint/Defender for Business capability sees a plain "requires Defender for Endpoint" banner instead of a wall of red for something it can't configure.
- **Key types:** `AsrRuleMode`, `AsrRuleState { ruleId, mode, sourcePolicyNames?, hasConflict? }` :  see [[Domain Types]]
- **Static catalog:** `src/lib/data/asr-rule-definitions.ts` :  `ASR_RULE_DEFINITIONS`, the 19 real rules (GUID, description, risk mitigated, category, Warn-mode/telemetry support, manual setup guidance), verified against Microsoft Learn's ASR rules reference.
- **Classifier:** `src/lib/services/asr-rule-matcher.ts` :  `classifyAsrRuleTier()` (has a test). A fresh 4-state enum (`critical`/`gap`/`in_progress`/`protected`), not a reuse of `MfaRiskTier` - this is rule configuration status, not user risk, and the states genuinely differ. Critical is reserved for a Standard Protection rule sitting at Not Configured.
- **Renders:** `Drawer` (same click-a-row-for-detail pattern as [[Intune Endpoint Security]] and [[Sign-In Logs & CA Diagnostics]]).
- **Server-only rule exclusion:** "Block Webshell creation for Servers" (the one rule with no Advanced Hunting telemetry at all, and only applicable to on-prem/hybrid Exchange servers) is excluded from the tier counts and the sidebar badge, tagged "Server Only" in the list instead - a pure-cloud tenant shouldn't see an inflated gap count for something it has no way to act on.
- **Sidebar badge:** `asrRuleGapCount` in `Sidebar.tsx`, computed the same way (via `classifyAsrRuleTier`, excluding the server-only rule) rather than re-deriving its own logic, and gated on the same `hasDefenderForEndpointCapability()` check as the module itself so an unlicensed tenant's nav doesn't show a misleading count.
- **MDE capability detection:** `hasDefenderForEndpointCapability(snapshot)` (`src/lib/utils/defender-for-endpoint.ts`) is the single shared gate used by both the module and the sidebar badge. It matches capability id `cap-mde` (the generic id a live-synced tenant's `capabilities-mapper.ts` always produces) as well as the mock-only `cap-mde-p1`/`cap-mde-p2` ids, plus a name-substring fallback, plus a tenant-tier fallback (`M365_E5`/`M365_BP`) for tenants with no matching capability entry at all - same defense-in-depth pattern as `ConditionalAccessModule.tsx`'s Entra P2 check. This was added after a live bug report: Business Premium tenants genuinely include Defender for Business (the SMB-scoped equivalent of Defender for Endpoint), but `capabilities-mapper.ts`'s `hasMde` SKU list didn't recognize the `SPB` skuPartNumber, and this module's own gate only ever checked the mock-only ids - so the ASR tab silently disappeared for every real Business Premium tenant regardless of licensing. Both root causes are fixed; see [[Domain Types]] for where `cap-mde` fits among the other capability ids.
- **Detection activity (Phase 2):** on mount, the module POSTs to `/api/tenants/[id]/asr-detections` (empty body) for a per-rule 30-day hit summary, rendered as a small `N events (30d)` badge next to the mode badge - deliberately not tier-colored, so a Block rule catching something reads as the system working, not a fault. Opening a rule's drawer POSTs again with `{ ruleId }` for that rule's raw recent events (cached per rule for the session), each expandable inline to show parsed `additionalFields`.

## Data flow for configuration state

Originally, "Phase 1" only ever shipped the UI/tiering/mock-data half of configuration-state reporting - there was no code anywhere that fetched real ASR rule configuration from a live tenant, so every live sync left `asrRules` `undefined` and every rule silently defaulted to Not Configured regardless of the tenant's actual state (a live bug report: "a client has business premium... but the ASR rule does not show" turned out to be this, not the MDE capability detection issue described above (both were real, independent bugs found back to back). This is now fixed - live tenants get real configuration data.

- **Three independent, mergeable Intune surfaces**, verified against Microsoft Learn and an official Microsoft GitHub sample (not guessed), since a real tenant can use any of them and Intune merges all that apply into one superset per device:
  1. **Settings Catalog** (`Endpoint security > Attack surface reduction policy`, the modern format Microsoft's own docs say most tenants use today) :  `deviceManagement/configurationPolicies` filtered by `templateReference/templateFamily eq 'endpointSecurityAttackSurfaceReduction'`, then each policy's `/settings`. Rules are keyed by a human-readable slug in each setting's id (e.g. `..._blockexecutionofpotentiallyobfuscatedscripts_block`), not the GUID - the slug<->rule-GUID map is built at sync time from Microsoft's own tenant-agnostic catalog metadata (`deviceManagement/configurationSettings?$filter=rootDefinitionId eq '...'`, cached process-wide on `globalThis` the same way the Graph token is, since it's global Microsoft data, not per-tenant) cross-matched against `ASR_RULE_DEFINITIONS`' verified names, rather than 19 hand-typed guesses.
  2. **Legacy classic Device Configuration profile** (`Endpoint protection` profile, `windows10EndpointProtectionConfiguration`) :  simplest surface, each rule is a flat named top-level property (e.g. `defenderOfficeAppsLaunchChildProcessType`). Only 15 of the 19 catalog rules are expressible in this older schema (a Microsoft-side gap, not this app's) - see `LEGACY_ASR_PROPERTY_TO_RULE_ID` for the exact, verified allowlist. Deliberately NOT a generic `defender*Type` name match: `defenderNetworkProtectionType`/`defenderGuardMyFoldersType` match that naming pattern but are Network Protection/Controlled Folder Access, unrelated Defender features.
  3. **Older "Endpoint Security Templates" intents** (being phased out but not retired) :  same 15-rule schema as #2, reached via `deviceManagement/intents` `definitionValues` instead of a flat resource read. Reuses the intents list [[Intune Endpoint Security]] already fetches for antivirus/EDR policy counts, filtered by the same category-name-matching convention, rather than a second identical request.
- **Mapper:** `src/lib/services/asr-configuration-mapper.ts` (has a test) :  `buildAsrSlugMap()` (surface 1's slug<->GUID resolution), `mapAsrSettingDefinitionIdsToSignals()` (surface 1), `mapNamedPropertyValuesToSignals()` (shared by surfaces 2 and 3), and `mergeAsrRuleStates()` - the single cross-surface merge point every signal funnels through, always returning exactly 19 entries.
- **Conflict handling:** per Microsoft's documented ASR policy merge behavior, when two+ sources set a rule to *different* modes, the conflicting setting is dropped entirely rather than one source winning - so the effective mode is genuinely Not Configured, which is what `mergeAsrRuleStates()` returns. `AsrRuleState.hasConflict` is what keeps that distinguishable from a rule nobody has ever touched, since a self-canceling policy pair is a real, actionable misconfiguration - surfaced as a row-level badge and a drawer warning box in `AsrRulesModule.tsx`, listing every contributing `sourcePolicyNames` entry.
- **Graph calls:** `graph-client.ts`'s ASR configuration section (right after the existing Intune Endpoint Security intents fetch), one try/catch per surface, each pushing to `syncErrors` with its own `"ASR Rules (...)"`-prefixed message on failure. If every surface fails, `asrRules` is left untouched rather than overwritten with an empty result (preserves last-good data on a transient/permission failure, same guard every other optional sync section uses).
- **Sync error banner:** `AsrRulesModule.tsx` filters `snapshot.syncHealth.errors` for the `"ASR Rules"` prefix and renders it in the same rose-bordered banner style already established by [[Defender for Office 365 & TABL|MdoPoliciesModule]], since a false "Not Configured" reading here is unusually costly to trust.
- **No new admin consent needed:** `DeviceManagementConfiguration.Read.All`, already requested/tested for the existing Intune Endpoint Security permission, covers all three new endpoints.
- **Permanent limitations** (Graph can't see these, not a future TODO): ConfigMgr-managed (tenant-attach) devices, raw custom OMA-URI profiles not recognizable as the named ASR CSP path, and on-prem GPO not synced through Intune. Also, like every other policy-reporting module in this app (Conditional Access, Secure Score), this reports tenant-wide configured state, not per-device rollout - a rule assigned to only a pilot group still shows as configured tenant-wide.

## Data flow for detection activity
- **Types:** `AsrRuleActivitySummary`, `AsrDetectionEvent`, `AsrDetectionTimeRange` (`"7d" | "30d" | "all"`) :  see [[Domain Types]]. None of these are stored on `TenantSecuritySnapshot` - all on-demand only, never part of a tenant sync.
- **Mapper:** `src/lib/services/asr-detection-mapper.ts` (has a test) :  `mapActionTypeToRule()` resolves a raw Advanced Hunting `ActionType` (e.g. `AsrRansomwareBlocked`) back to a rule + bucket via `ASR_RULE_DEFINITIONS`' `advancedHuntingActionTypes` lists; `buildActivitySummaries()` zero-fills the full 19-rule array from an aggregate query's `{ActionType: count}` shape; `synthesizeMockActivity()` generates deterministic (hashed, not random) demo numbers for mock tenants, scaled by the selected `AsrDetectionTimeRange` (7d = 0.25x, 30d = 1x/baseline, all = 3x) - always zero for a Not Configured rule or the no-telemetry Webshell rule, since a rule that isn't enforcing anything can't have logged a detection.
- **Time range selector (added after a live user report of "no events shown"):** the module previously hardcoded a 30-day window everywhere with no way to change it. `AsrRulesModule.tsx` now has a "Detection Activity Summary" section (aggregate totals across all 19 rules - Total Events/Blocked/Audited/Rules With Activity) with a 7 Days / 30 Days / All Time selector; the same `timeRange` state also drives the per-row `N events (Xd)` badges and a matching selector inside the rule drawer. "All Time" isn't literally unlimited - it requests a generous 180-day window (`ASR_TIME_RANGE_TO_KQL_DAYS`/`ASR_TIME_RANGE_TO_TIMESPAN` in `graph-client.ts`) and lets Graph return whatever Advanced Hunting's own retention actually kept (30 days by default, longer only if the tenant has configured extended retention), rather than this app guessing a tenant's real retention setting. `fetchAsrDetectionSummaries`/`fetchAsrDetectionEvents` both take an optional `timeRange` param (default `"30d"`, so every existing caller/test stays valid unchanged); the events-drawer cache key is now `${ruleId}:${timeRange}` so switching ranges while a drawer is open refetches instead of showing a stale, now-mislabeled range's cached events.
- **Graph calls:** `graph-client.ts`'s `fetchAsrDetectionSummaries`/`fetchAsrDetectionEvents`, mirroring `deployConditionalAccessPolicy`'s mock-short-circuit-first shape. Live path is `POST https://graph.microsoft.com/v1.0/security/runHuntingQuery` (v1.0, not beta) with a KQL query against `DeviceEvents`, requiring `ThreatHunting.Read.All` - a materially more restrictive permission than anything else this app requests, so a missing-permission response is treated as an expected, graceful `{ error }` outcome, not a thrown exception.
- **Missing-permission error, rewritten:** Graph's raw 403 for this endpoint reads "Missing application roles. API required roles: ThreatHunting.Read.All, application roles: <every other permission the app holds>" - accurate but reads as "the app is broken" rather than "this one optional permission was never granted," per a live user report. `classifyAdvancedHuntingError()` (pure, tested in `graph-client.test.ts`, called from the shared `runHuntingQuery()` helper both detection functions use) pattern-matches this specific 403 shape and rewrites it into an actionable message naming the missing permission, the license requirement, where to grant it, and that everything else in the module already works without it - the same rewrite convention `deployConditionalAccessPolicy()` uses for CA05's two failure modes.

- **False-negative bug, found and fixed: the permission self-test itself could report "missing" for a genuinely-granted permission.** A live user report: a tenant had `ThreatHunting.Read.All` confirmed granted in Entra, yet Clarity365's own Permissions modal still showed it as missing, and the module's real query failed with `'where' operator: Failed to resolve table or column expression named 'DeviceEvents'. Fix semantic errors in your query.` - a 400 KQL semantic error, not a 401/403 auth error. Root cause: `testAppRegistrationPermissions`' self-test probe queried `DeviceEvents | where Timestamp > ago(1d) | take 1` directly, and the self-test loop treats ANY non-2xx response as "missing" regardless of *why* it failed. Device-level Advanced Hunting tables like `DeviceEvents` require a Defender for Endpoint P1/P2 (or equivalent E5) license specifically - **Defender for Business tenants can have the permission fully granted and still get a table-resolution 400**, since that table simply isn't exposed on their plan. The self-test's probe query was conflating "permission not granted" with "this specific table isn't on this tenant's plan," and reporting both as the same "missing" outcome.
  - **Fix:** the self-test's `ThreatHunting.Read.All` entry now sends a table-independent Kusto literal, `print ClarityPermissionProbe = 1` - no `from`/table reference at all, so its result depends solely on whether the permission itself is granted, never on which Advanced Hunting tables happen to resolve for a given tenant/plan. `classifyAdvancedHuntingError()` also gained a second branch: any `Failed to resolve table or column expression named '<table>'` message (regardless of which table) is rewritten into a message that explicitly says the permission is fine and points at checking security.microsoft.com to confirm the table's real availability, rather than telling the admin to go grant a permission that's already granted.
  - **Correction - the original "Defender for Business lacks this table" theory was disproven live, not just softened as a caveat.** The first version of this fix (and its rewritten error message) confidently attributed the table-resolution failure to Defender for Business categorically lacking device-level Advanced Hunting tables, based on third-party community answers. A live user directly disproved this for their own Business Premium tenant (Axiomatic): they can see the exact same ASR detection data in the Defender portal's own **Reports > Attack Surface Reduction Rules > Detections** page, which a "this table doesn't exist on this plan" explanation cannot account for. The rewritten message for this case is now deliberately non-committal about the root cause instead of asserting a specific (and, for at least one real tenant, wrong) explanation.
  - **What the live investigation actually found instead:** re-testing against Axiomatic surfaced a *different* error than the one that prompted this whole fix - `Lifetime validation failed, the token is expired` (HTTP 401), not the table-resolution 400. A temporary diagnostic (added to `graph-client.ts`/`tenant-store.ts`, later removed) proved this is not Clarity365's own token caching: a token fetched and used within the same second was still rejected the same way, and the error had already changed from Case 1's "missing application roles" 403 (seen before the permission was granted) to this different error (seen after) - meaning Graph's own authorization check for `ThreatHunting.Read.All` is passing, and something *downstream* of that still rejects the token. `classifyAdvancedHuntingError()` gained a third branch for this exact message.
  - **Resolution - this was never actually an ASR-specific or Defender/XDR-specific issue.** The "propagation delay to the Defender/XDR backend" hypothesis above didn't survive the next report: the SAME "Lifetime validation failed, the token is expired" error started appearing on **every single Graph endpoint** for Axiomatic (Conditional Access, Users, Groups, SharePoint, everything - checked directly via the Permissions modal, not just ASR). That rules out anything specific to `runHuntingQuery` or the Defender/XDR backend - a bad credential affecting a tenant's every Graph call reads identically whether the first symptom noticed happens to be ASR detection activity or something else entirely. The real cause was the Axiomatic tenant's own Entra app registration credentials (client secret rotated/expired/revoked on the client's side) - see [[Tenant Store]] and `EditTenantCredentialsModal` in [[Modals]] for the fix (a UI to rotate stored credentials, which didn't exist anywhere in the app until this incident surfaced the gap). The `classifyAdvancedHuntingError()` Case 3 message above is still accurate as far as it goes (a fresh token really was being rejected, and that really did rule out Clarity365's own caching) but undersells how broad the underlying cause could be - a future instance of this exact message should prompt checking the Permissions modal for whether it's actually tenant-wide before assuming it's specific to Advanced Hunting.
  - **Why this matters for other tenants:** the recurring lesson here isn't "Defender for Business lacks a table" (that claim didn't survive contact with a real tenant) - it's that this endpoint's error modes are varied and not fully understood yet, so every rewrite in `classifyAdvancedHuntingError()` should state only what's actually been confirmed, and default to suggesting the admin check the Defender portal directly rather than asserting a specific Microsoft-side cause with false confidence.
  - **Final root cause, confirmed (not just "the client's secret was bad"):** rotating Axiomatic's secret via the new `EditTenantCredentialsModal` didn't fix anything on the first attempt - the Permissions modal kept showing the identical `"Lifetime validation failed"` error, letter for letter, which is the tell that a *different*, valid secret was never actually being tried. Cause: `getGraphAccessToken()`'s in-memory token cache is keyed by `tenantId:clientId` only, not by the secret - so rotating just the `clientSecret` (the common case) left the OLD cached token (acquired under the bad secret) being served indefinitely, since the cache is purely time-based and had no way to know the credentials underneath it had changed. Fixed by a new `invalidateGraphTokenCache()` (exported from `graph-client.ts`), called from `tenant-store.ts`'s `updateTenant()` whenever a `credentials` update is applied (both the old and new `tenantId:clientId` pair are cleared, in case those changed too, not just the secret). Confirmed live: after this fix, resaving Axiomatic's credentials (even re-submitting the same values) forced a fresh token fetch, and the Permissions check flipped to `all_granted` across every single permission. See [[Tenant Store]] for the fix in the store layer.
- **Orchestration:** `tenant-store.ts`'s `getAsrDetectionSummaries`/`getAsrDetectionEvents`, same decrypt-then-delegate shape as `testPermissions`/`testExoConnectivity` - both now also take the `timeRange` param and thread it through.
- **Permissions self-test:** `ThreatHunting.Read.All` is now tested by `testAppRegistrationPermissions` (`graph-client.ts`) - a live tenant that hasn't granted it sees this surfaced as an explicit, expected, optional gap in the Permissions modal (and in `AddTenantModal.tsx`'s setup guidance) rather than only discovering it via the module's own detection-activity error text (see the rewrite above). `PermissionTestResult` gained `method`/`body` (defaulting to GET) specifically to support this - `runHuntingQuery` has no GET form, so this was the one existing permission needing a POST-based self-test; the check itself runs a minimal, cheap query (`DeviceEvents | where Timestamp > ago(1d) | take 1`) rather than anything resembling the real 30-day aggregate. Marked `optional: true` (excluded from the pass/fail rollup) since ASR rule configuration reporting is fully unaffected without it - only the event-count badges and event list are unavailable.

## Scope: Phase 3 (write path) - done
Phase 1 (config-state reporting), Phase 2 (detection activity), and Phase 3 (deploy) are all done. The "Deploy ASR Rules" button in the module header (shown only when `Tenant.endpointSecurityWriteMode === "write_enabled"`) opens a drawer with a per-rule Block/Audit/Warn/Not Configured picker (new rules default to Audit, never Block) and an assignment picker (Do Not Assign / Assign to All Users / Assign to All Devices / Assign to All Users and Devices / a specific group - all five, matching Intune's own picker exactly, see [[Defender Configuration & Onboarding]]'s note on `IntuneAssignmentTarget` gaining `allUsersAndDevices`), then POSTs to `/api/tenants/[id]/endpoint-security/asr-deploy`.

Deploys via the **same Settings Catalog surface** the read path already resolves (`deviceManagement/configurationPolicies`, `templateReference.templateFamily: "endpointSecurityAttackSurfaceReduction"`), not `deviceManagement/intents` as originally planned - the intents-based Endpoint Security Template surface is Microsoft's own being-phased-out format, so writing to the Settings Catalog instead (the same surface most tenants are already read from) was the more useful target. `graph-client.ts`'s `deployAsrRulePolicy()` inverts the same slug<->ruleId map `getAsrSettingsCatalogSlugMap()` builds for reads, and the pure `buildAsrRuleSettingsChildren()` (tested in `graph-client.test.ts`) builds the per-rule `groupSettingCollectionValue` children. The `_audit`/`_block`/`_warn` choice-value suffix convention was confirmed against a real deployed Settings Catalog ASR policy (a public OpenIntuneBaseline export), not guessed - notably `_audit`, not `_auditmode` (the read-side mapper tolerates both since it predates this confirmation).

Assignment uses the standard Intune `assignments` array (`allDevicesAssignmentTarget`/`allLicensedUsersAssignmentTarget`/`groupAssignmentTarget`), POSTed separately via `.../configurationPolicies('{id}')/assign` - `buildIntuneAssignmentTarget()` (also in `graph-client.test.ts`) builds this. Gated behind the same two gates as [[Defender Configuration & Onboarding]]'s write path: `endpointSecurityWriteMode` and `DeviceManagementConfiguration.ReadWrite.All`.

Each rule's drawer still shows manual setup guidance (PowerShell + Intune portal steps) sourced from `ASR_RULE_DEFINITIONS`, for tenants that stay in Read-Only mode.

**Fixed live user report (2026-09-18): the Read-Only banner named the module to toggle Write-Enabled mode in, but gave no way to get there.** "Turn on Write-Enabled mode in the Defender Config & Onboarding module" was plain text - `AsrRulesModule.tsx` never received an `onNavigate` prop at all, unlike [[Conditional Access Policy Scanner]] and [[Secure Score & Timeline]], both of which already had one for the same purpose. User reported "not able to click to edit or read-only," which traced directly to this: they were trying to click that sentence expecting it to jump to the toggle. Added `onNavigate?: (view: string) => void` to `AsrRulesModuleProps`, wired from `AppShell.tsx` the same way as the other two modules, and made the module name a real button (`onNavigate("defender_config")`) when the prop is provided, falling back to plain text otherwise. Checked `IntuneSecurityModule.tsx` for the same gap since it's the other module touching endpoint security - it has no cross-module banner at all (device compliance reporting only), so nothing to fix there.

**Update-in-place fix (found via a user question, not a live bug report):** `deployAsrRulePolicy()` originally only ever `POST`ed a brand-new Settings Catalog policy - clicking "Deploy ASR Rules" a second time created a duplicate rather than updating the first one, the same latent bug found in [[Defender Configuration & Onboarding]]'s AV/EDR deploys. The "which policy is this replacing" half of the fix is wired the same way it always was: unlike AV/EDR, ASR's own read path (`Data flow for configuration state` above) merges rule state across three surfaces and can legitimately see multiple pre-existing Settings Catalog ASR policies this app never created, so blindly targeting "the first one found" during a redeploy could silently touch another admin's or tool's unrelated policy. A `clarity365AsrPolicyId` field on `TenantSecuritySnapshot.intune` (see [[Domain Types]]) tracks only the id of the policy *this app itself* created, set the moment `tenant-store.ts`'s `deployAsrRules()` succeeds and never inferred from the general multi-surface sync - so a redeploy only ever touches a policy Clarity365 knows it made. The button reads "Redeploy ASR Rules" once that field is set.

**The "how do you actually replace it" half was wrong and has been corrected - see [[Defender Configuration & Onboarding]] for the full live investigation.** The original fix PATCHed `deviceManagement/configurationPolicies/{id}` with `{ settings }` alone; Graph's own `$metadata` confirms `settings` is a `NavigationProperty` with no bound update operation at all, and Intune's real backend rejects even a per-item PATCH on the settings collection with "No OData route exists ... with http verb PATCH" - the operation was never built, not misconfigured. `deployAsrRulePolicy()` now calls the same `createSettingsCatalogPolicyReplacing()` helper AV/EDR use: create the new policy, assign it, then delete the old `clarity365AsrPolicyId` - live-verified end-to-end (on the EDR path; ASR shares the identical helper and Graph resource, so the same mechanism applies).

## Known issue, found live but not yet fixed: the Settings Catalog slug match can silently break tenant-wide

Live-verifying the EDR policy work (see [[Defender Configuration & Onboarding]]) surfaced a real ASR regression on Axiomatic: the module's own sync-error banner now reads `"ASR Rules (Settings Catalog): 19 rule(s) in Microsoft's catalog could not be matched to a known ASR rule - they will be skipped rather than misattributed."` - i.e. **zero** of the 19 rules matched, tenant-wide, for the Settings Catalog surface specifically.

Root cause (not yet fixed, worth checking before trusting ASR state on any tenant): a live Settings Catalog category dump for an unrelated lookup happened to also return ASR rule metadata, and displayNames there carry a `" (Device)"` suffix Microsoft evidently added at some point - e.g. `"Block abuse of exploited vulnerable signed drivers (Device)"`, not the plain name `buildAsrSlugMap()`'s `normalizeForMatch()` compares against. Since `normalizeForMatch()` only strips non-alphanumeric characters (`.replace(/[^a-z0-9]/g, "")`), the suffix survives normalization as literal `...signeddriversdevice`, which no longer equals `ASR_RULE_DEFINITIONS`' `...signeddrivers` - so the match silently fails for every rule carrying this suffix. This is a live, tenant-side Microsoft catalog wording change breaking a previously-working name-based match, not something this session's code changes caused.

The safety net worked as designed (the mismatch was reported via `syncErrors`, not silently misattributed - see `buildAsrSlugMap`'s own doc comment), but a 0/19 match rate self-evidently defeats the read path's purpose. Fix, not yet done: either strip a trailing `" (Device)"`/`" (User)"`-style suffix in `normalizeForMatch()` before comparing (cheap, matches the pattern already seen on OneDrive settings in the same catalog dump), or match on `rootDefinitionId`'s slug portion instead of `displayName` entirely (more robust, avoids depending on wording Microsoft can change again). Whichever tenant reports this next, check this note first before re-diagnosing from scratch.
