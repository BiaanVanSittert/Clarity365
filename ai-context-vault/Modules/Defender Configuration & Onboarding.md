# Defender Configuration & Onboarding

Phase 1 (read-only) of a two-phase Endpoint Security expansion: Microsoft Defender for Endpoint connector settings, per-device MDE onboarding status, and an Intune/EDR coverage-gap report. Sibling to [[Intune Endpoint Security]] and [[Attack Surface Reduction Rules]], not a replacement for either.

- **Component:** `DefenderConfigurationModule.tsx`
- **Reads:** `TenantSecuritySnapshot.intune.mdeConnectorSettings`, `.onboardingStates`, `.devices`, `.accountClassification.users` (all prop-driven, no direct fetch)
- **Key types:** `MdeConnectorSettings`, `AtpOnboardingDeviceState`, `IntuneCoverageGaps`, `EndpointSecurityWriteMode` - see [[Domain Types]]
- **Uses service:** `src/lib/services/intune-coverage-analyzer.ts` (new, tested) - `computeIntuneCoverageGaps()`

## Verified Graph surfaces (checked against Microsoft's own API reference, not guessed)

**MDE connector settings** - `deviceManagement/mobileThreatDefenseConnectors` (beta, for the full property set - v1.0 alone omits macOS and a few iOS/Windows fields). Nearly every toggle in Intune's "Defender and MEM Reporting" blade maps to a real property (`microsoftDefenderForEndpointAttachEnabled`, `partnerUnsupportedOsVersionBlocked`, per-platform `androidEnabled`/`iosEnabled`/`windowsEnabled`/`macEnabled`, the matching `*DeviceBlockedOnMissingPartnerData` block-on-unavailable flags, `*MobileApplicationManagementEnabled` for MAM, and the iOS app/certificate metadata collection flags). Every label in `DefenderConfigurationModule.tsx`'s connector section is Microsoft's own wording, verbatim where confirmed against the live Intune admin center or `configure-integration.md` (flagged inline per-row in code comments where it's a close paraphrase instead) - per an explicit user request to see exactly what each toggle is, not a shortened version.

**Correction: "Connect Defender Configuration Package automatically" and "Enable Sample Sharing" are real, Graph-configurable, assignable settings - the original claim that both were non-configurable was wrong.** They aren't connector-level settings at all - they belong to a separate, genuinely assignable Intune policy resource ("Endpoint detection and response", Settings Catalog category "Microsoft Defender for Endpoint") that this module didn't model in Phase 1. Confirmed live via a temporary tenant-agnostic Settings Catalog category/setting lookup (`deviceManagement/configurationCategories` + `configurationSettings`, later removed) rather than trusted from docs alone - the exact settingDefinitionIds and choice values are `device_vendor_msft_windowsadvancedthreatprotection_configurationtype` (choice value `..._autofromconnector`) and `device_vendor_msft_windowsadvancedthreatprotection_configuration_samplesharing` (`_1`/`_0` for All/None). See the new "EDR Policy" section below - the only genuinely non-configurable-via-Graph item left is **Mobile Threat Defense role** (Android COBO/COPE), unchanged.

**Per-device onboarding status** - `deviceManagement/advancedThreatProtectionOnboardingStateSummary/advancedThreatProtectionOnboardingDeviceSettingStates` (beta) - the direct Graph equivalent of Intune's "EDR Onboarding Status" report tab. This same fetch also feeds [[Intune Endpoint Security]]'s `edrOnboardingState` field now (see that note) - one fetch, two consumers, not duplicated.

Both are fetched as steps 18/19 of `fetchLiveTenantSnapshot` (bumping `TOTAL_SYNC_STEPS` from 17 to 19) - cheap enough (one object; one device-count-sized list, the same order of magnitude as the device inventory already synced every time) to ride along in the main sync rather than needing an on-demand fetch like ASR detection events does.

## Coverage gaps

Two pure lenses in `intune-coverage-analyzer.ts`, both reused by the Sidebar badge (`defenderCoverageGapCount`) so the nav count and the module's own numbers can never disagree:
- **Users missing from Intune**: licensed, enabled users **whose own assigned license is actually Intune-capable**, with zero devices in `intune.devices` matching their UPN.
- **Devices missing EDR/AV**: devices whose `edrOnboardingState` isn't `onboarded` - deliberately excluding `unsupported` (a platform MDE genuinely can't onboard isn't a closeable gap, so flagging it would be noise).

**Fixed live user report (2026-09-18): "licensed" alone isn't "Intune-capable."** `findUsersMissingIntuneDevice()` originally flagged *any* licensed, enabled user with no enrolled device - a user on Exchange Online Kiosk, or any other SKU with no Intune/EMS entitlement at all, got flagged identically to someone on Business Premium or E3/E5, even though there's no closable gap for them. Fixed by reusing `capabilities-mapper.ts`'s already-live-verified per-tenant Intune SKU rule, now extracted into `isIntuneCapableSkuPartNumber()` (and its `isBusinessPremiumSku()` helper, covering the "O365_BUSINESS_PREMIUM is legacy branding for Business Standard, not Premium" trap) so both the tenant-wide capability check and this per-user check apply the identical rule instead of each carrying its own copy that could drift apart - the same "extract a shared pure function" convention as `hasEntraP2Capability()`/`hasDefenderForEndpointCapability()` (see [[Attack Surface Reduction Rules]], [[Conditional Access Policy Scanner]]).

## Read-only vs. write-enabled: two gates

`Tenant.endpointSecurityWriteMode` (`"read_only" | "write_enabled"`, defaults to read-only) is a deliberate per-tenant choice - a plain toggle in this module's header, persisted via the existing `PUT /api/tenants/{id}` route (already does a partial `Tenant` merge, no new route needed). This is one of *two* independent gates for Phase 2's not-yet-built deploy actions - the other being the `DeviceManagementConfiguration.ReadWrite.All` Graph permission. Both must be satisfied; neither implies the other. Phase 1 (this note) ships with the toggle wired up but nothing yet gated behind it, since there's nothing to deploy - built ahead of Phase 2 so the choice exists before the feature that needs it does.

## Sequencing

Phase 1 (read-only reporting) and Phase 2 (write-enabled deploy) are both done.

**Phase 2 - what actually shipped:**
- **MDE connector setting writes:** `graph-client.ts`'s `updateMdeConnectorSettings()` PATCHes `deviceManagement/mobileThreatDefenseConnectors/{id}` directly - no report-only concept exists for this resource (a single tenant-wide live setting), so the UI (`DefenderConfigurationModule.tsx`) requires a `window.confirm()` "takes effect immediately, tenant-wide" before firing, per-toggle, only on the boolean fields that make sense to flip live (General/Windows/Android/macOS "connect to MDE" and "block on unavailable" fields; MAM/cert-sync fields stay read-only since flipping those has broader Intune-side implications not modeled here).
- **Defender Antivirus policy:** **not** a generalization of the ASR slug-map mechanism as Phase 1's plan originally assumed - correction recorded in `Optimization Plan.md`. The settings are independent, flat `settingDefinitionId` strings (`DEFENDER_AV_SETTING_DEFINITION_IDS` in `graph-client.ts`), not a collection needing dynamic slug resolution like ASR. `fetchDefenderAvPolicy()`/`deployDefenderAvPolicy()` read/write via `deviceManagement/configurationPolicies` filtered by `templateReference.templateFamily eq 'endpointSecurityAntivirus'`, reusing `flattenSettingsCatalogSelectedIds()` unchanged on the read side. The pure `buildDefenderAvSettingsPayload()` (tested in `graph-client.test.ts`) confirmed the boolean choice-value suffix is `_1`/`_0` (enabled/disabled) - a different convention from ASR's `_block`/`_audit`/`_warn`.
  - **Live catalog verification (same lookup as the EDR policy above) caught two wrong ids and one missing field, all now fixed:** `allowFullScanOnRemovableDrives` was guessed as `...allowfullscanonremovabledrivescanning` (with "on") - the real id has no "on". `allowUpdatesOnMeteredNetwork` was guessed under the wrong CSP root entirely - the real id is `device_vendor_msft_defender_configuration_meteredconnectionupdates`, same root as `disableLocalAdminMerge` (which turned out to be correct, no longer flagged unconfirmed). `allowCloudProtection` was in the user's original request but never actually added as a field - added now (`device_vendor_msft_policy_config_defender_allowcloudprotection`). Every AV checkbox label in `DefenderConfigurationModule.tsx` is now Microsoft's own Settings Catalog `displayName`, verbatim, not paraphrased.
- **EDR Policy (new):** `fetchEdrPolicy()`/`deployEdrPolicy()` in `graph-client.ts`, mirroring the AV policy functions exactly, targeting `templateReference.templateFamily: "endpointSecurityEndpointDetectionAndResponse"` (following the same `endpointSecurity<Name>` convention as AV/ASR, but *not* independently confirmed via a real deployed example the way those two were - verify live before trusting the templateFamily string specifically). Models only "Auto from connector" (the recommended, no-file-upload option - "Onboard"/"Offboard" both need a signed blob pasted in, out of scope) and "Sample Sharing" (All/None). New `EdrPolicySettings` type - see [[Domain Types]]. UI section "EDR Policy" in `DefenderConfigurationModule.tsx`, same shape as the AV policy section (current state, checkboxes, assignment picker, Deploy/Redeploy). Live-verified against Axiomatic: the tenant already had a real EDR policy deployed with "Auto from connector" configured, and the read-back correctly detected it.
  - **Bug found and fixed via a real failed deploy, not guessed:** the first live deploy attempt on Axiomatic failed - Graph rejected `AutoFromConnector` with `"...with dependent settings doesnt contain required dependent settings. Required dependent settings are device_vendor_msft_windowsadvancedthreatprotection_onboarding_fromconnector"`. Looked up that dependent setting's exact shape live (a `deviceManagementConfigurationSimpleSettingInstance` holding a `deviceManagementConfigurationSecretSettingValue`, not a choice) rather than guessing it, and added it as a required `children` entry under the `configurationtype` choice value in `buildEdrPolicySettingsPayload()` - `value: "AutoFromConnector"`, `valueState: "notEncrypted"` (the only valid enum member for a plaintext value being submitted fresh; `"invalid"` is Graph's own empty-state sentinel, `"encryptedValueToken"` is only for round-tripping a value Graph already encrypted). Re-tested live immediately after the fix - deploy succeeded. This dependency is a Graph schema requirement, not tenant-specific, so the fix is universal (every tenant needs this same child setting, not just Axiomatic) - regression test in `graph-client.test.ts` uses the exact real error text captured live.
  - **Error message readability, fixed generally, not just for this one error:** the raw error the deploy failure surfaced in the UI was a full JSON blob (`{"_version": 3, "Message": "...", "CustomApiErrorPhrase": "", ...}`), because Intune's Settings Catalog backend (`deviceManagement/configurationPolicies`) puts its own raw error body as the literal string value of Graph's `error.message` field instead of a clean sentence - not a bug in Clarity365's own error handling, which was already correctly surfacing whatever `error.message` contained. New pure `cleanIntuneConfigV2Error()` (tested with the real captured error text) extracts just the `.Message` field when the raw text parses as this shape, applied to every Settings Catalog write path in `graph-client.ts` (AV policy, EDR policy, ASR rules, the `/assign` call, and the MDE connector PATCH for consistency) - not just the one error that happened to surface first, so a *different* future Graph rejection (a new required dependency, a different validation failure) also shows a readable sentence instead of a raw dump. Falls back to the original text completely unchanged whenever it doesn't match this shape, so nothing is ever hidden.
- **ASR rule deployment:** documented in [[Attack Surface Reduction Rules]] (its own Phase 3), not duplicated here.
- **Assignment picker, corrected to match Microsoft's real options:** previously only exposed "Do Not Assign" / "All Devices" / "a specific group", missing two of Intune's four canonical choices. `IntuneAssignmentTarget.mode` gained `"allUsersAndDevices"` (sends both `allLicensedUsersAssignmentTarget` and `allDevicesAssignmentTarget` in one `assignments` array); the picker now shows all five options with Microsoft's own wording ("Assign to All Users" / "Assign to All Devices" / "Assign to All Users and Devices"), shared as `ASSIGNMENT_MODE_OPTIONS` between the AV and EDR sections in this file, and duplicated (small, static array - not worth a cross-file import) in `AsrRulesModule.tsx`'s own deploy drawer.
- **UI:** `DefenderConfigurationModule.tsx` gained per-toggle edit controls on the MDE connector section and "Defender Antivirus Policy"/"EDR Policy" sections (current state, a checkbox form, assignment picker defaulting to "no assignment yet", Deploy/Redeploy button) - all only rendered when `endpointSecurityWriteMode === "write_enabled"`.
- **New permission:** `DeviceManagementConfiguration.ReadWrite.All`, optional + write-access, tested via the same endpoint as its `.Read.All` counterpart (mirrors how `Policy.ReadWrite.ConditionalAccess` is tested) - see [[Core Graph Layer]].
- **Update-in-place fix (found via a user question, not a live bug report) - first version wrong, corrected after a second live report.** `deployDefenderAvPolicy()`/`deployEdrPolicy()` originally only ever `POST`ed a brand-new Settings Catalog policy on every call - the "Redeploy Policy" button's label already implied an in-place update, but it was calling the exact same create-only function, so every click silently created another duplicate AV/EDR policy in Intune instead of updating the existing one. **The first fix attempt PATCHed `deviceManagement/configurationPolicies/{id}` with `{ settings }` alone - this cannot work and was never actually exercised at the time**, because a concurrent, unrelated token bug (see [[Core Graph Layer]]'s "Lifetime validation failed" correction) was failing every redeploy attempt at the auth layer, before the request ever reached Graph's own schema validation. Once that token bug was fixed, the PATCH attempt finally reached Graph for real and came back with `"Cannot apply PATCH to navigation property 'settings' on entity type 'microsoft.management.services.api.deviceManagementConfigurationPolicy'."` A live investigation (Coetzee Architects) confirmed via Graph's own beta `$metadata` that `settings` is declared as a `NavigationProperty` (`ContainsTarget="true"`) on this entity, with **no bound Action/Function for updating it at all** - every action bound to `deviceManagementConfigurationPolicy` was checked (`assign`, `createCopy`, `reorder`, two enrollment-target actions, one baseline-retrieval function) and none touch settings. A follow-up test confirmed PATCHing an individual settings item by its own id (`.../settings('0')`) is *also* rejected outright by Intune's real backend (`DCV2GraphService`) with `"No OData route exists ... with http verb PATCH"` - not a validation error, a route that was never built. **Real fix: create a new policy, assign it, then delete the old one** (`createSettingsCatalogPolicyReplacing()` in `graph-client.ts`, shared by all three Settings Catalog deploy functions) - sequenced create-first-then-delete-old so a create failure never costs the tenant its existing policy, and a delete failure (rare, logged as a warning, `success: true` regardless) leaves at worst a harmless duplicate rather than a gap. Live-verified end-to-end against Coetzee: created a new EDR policy with a changed setting, assigned it "Do Not Assign", deleted the old one, confirmed exactly one policy remained with the new value. The identical fix, adapted for a real multi-policy-ambiguity risk specific to that surface, is documented in [[Attack Surface Reduction Rules]]. **The tell for next time:** a request that fails before it ever reaches the service being tested (here, an auth failure) proves nothing about whether that request's own shape is correct - a fix "verified" only by the absence of a *different* error can still be completely wrong underneath.
- **New API routes:** `GET/POST /api/tenants/[id]/endpoint-security/defender-av-policy`, `GET/POST .../edr-policy`, `GET/POST .../bitlocker-policy` (see BitLocker note below), `POST .../asr-deploy` (see ASR note), `PATCH .../mde-connector` - each mirrors `deploy-ca/route.ts`'s shape and independently checks `endpointSecurityWriteMode === "write_enabled"` before calling Graph (the permission gate itself isn't re-checked server-side, same convention as `deploy-ca`).
- **BitLocker policy (new, added by user request after EDR/AV were confirmed working):** `fetchBitLockerPolicy()`/`deployBitLockerPolicy()` in `graph-client.ts`, mirroring `fetchDefenderAvPolicy()`/`deployDefenderAvPolicy()` exactly (including `createSettingsCatalogPolicyReplacing()` for updates - see the correction above, this is the first of the three write paths built *after* that correction, so it never went through the broken PATCH-in-place phase). Uses the direct BitLocker CSP category (`Device/Vendor/MSFT/BitLocker`) confirmed live via the same tenant-agnostic category/setting lookup technique AV/EDR used - explicitly the CSP category (id `0a1347d2-90c0-407a-baa0-e4859260532a`, 5 settings), not the separate "BitLocker Drive Encryption" Administrative Templates/GPO category (id `0d37dddd-...`, 3 child categories) that also matched a "BitLocker" name search. `templateFamily: "endpointSecurityDiskEncryption"` confirmed against the real beta `$metadata` enum (`deviceManagementConfigurationTemplateFamily`, member value 11) rather than guessed by convention the way EDR's originally was.
  - **Models 4 of the CSP's 5 settings** (`BitLockerPolicySettings` - see [[Domain Types]]): Require Device Encryption, Allow Standard User Encryption, Allow Warning For Other Disk Encryption, and Configure Recovery Password Rotation (a real 3-way choice: off/Entra-ID-only/both-Entra-and-hybrid, confirmed live - not a boolean). Deliberately excludes the 5th, `RemovableDrivesExcludedFromEncryption` - a free-form comma-separated hardware-ID list, not a simple toggle, same reasoning EDR uses to exclude Onboard/Offboard.
  - **A real, documented functional pairing, not a Graph schema dependency:** Microsoft's own setting description says Allow Standard User Encryption only takes effect when Allow Warning For Other Disk Encryption is also explicitly `0` (silent encryption) - checked live whether this was a *hard* dependency the way EDR's onboarding child setting was (Graph would reject one without the other) and confirmed it is not; Graph accepts either independently, so this is a UX/documentation concern for the recommended preset, not something `buildBitLockerSettingsPayload()` needs to enforce.
  - **`RECOMMENDED_BITLOCKER_POLICY` lives in `types/index.ts`, not `graph-client.ts`** - deliberately, since `graph-client.ts` is server-only and the UI needs to import this constant directly for its "Use Recommended Settings" button without pulling in any server module. Sets Require Device Encryption + Allow Standard User Encryption on, Allow Warning For Other Disk Encryption off (the functional pairing above), and Recovery Password Rotation to both-Entra-and-hybrid (Microsoft's own stronger-than-default option). Surfaced as a one-click preset that fills the draft form, never applied silently - the admin still has to review and click Deploy.
  - **UI:** a third section in `DefenderConfigurationModule.tsx`, "BitLocker Policy", identical shape to the AV/EDR sections (current state, checkbox/radio form, "Use Recommended Settings" button, assignment picker, Deploy/Redeploy button).
