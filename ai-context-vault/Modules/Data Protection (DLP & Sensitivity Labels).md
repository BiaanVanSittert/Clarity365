# Data Protection (DLP & Sensitivity Labels)

A guidance library, not a live posture module - deliberately unlike every other entry in [[Clarity365 MOC#Modules|Modules]]. See [[Optimization/DLP & Sensitivity Labels Plan|DLP & Sensitivity Labels Plan]] for the full multi-stage plan and the 2026-09-22 decision that put this module here first.

- **Component:** `DataProtectionModule.tsx`
- **Sidebar:** its own top-level group, "Data Protection" - deliberately not nested under Collaboration & Governance (where it first shipped), per explicit user request the same day
- **Reads:** nothing from `TenantSecuritySnapshot`. Its only prop is `tenant` (optional), used solely to personalize the generated PowerShell script's policy-name prefix. This is intentional, not a placeholder - see "Why no snapshot" below.
- **Data source:** `src/lib/data/data-protection-recommendations.ts` - `DATA_PROTECTION_RECOMMENDATIONS`, one entry so far (`popia-sa-id-and-health`)

## What it does
Lets an admin filter by regulation and data category, then shows one recommendation pack: which built-in Sensitive Information Types to select in the Purview portal, the DLP rule logic and actions, numbered click-by-click portal steps, a best-effort Security & Compliance PowerShell script (copy-to-clipboard, same convention as `AsrRulesModule.tsx`'s `handleCopyGuidance`), E5-only enhancements kept separate from the base recommendation, the regulation citations behind it, and explicit caveats.

## Why no snapshot, no write path
Per the 2026-09-22 decision recorded in the plan: Clarity365 never writes DLP policies or labels via API for this feature - every recommendation is applied by hand in the Purview portal. This also means the module doesn't need a live Purview connection to be useful, so it was built and shipped *before* Stage 0/1's live-sync work, not after - see the plan's "Delivery order (revised 2026-09-22)" section. The live compliance-API connectivity check (Stage 0) was inconclusive (see the plan for the finding) but doesn't block this module, since it never depended on that connection.

## Content status
**9 recommendations shipped (2026-09-22).** All seven data categories from the original plan are covered, plus one added after user review:
- `popia-sa-id-and-health` - POPIA, SA ID number + health data
- `hipaa-phi` - HIPAA, PHI (SSN + ICD codes). Deliberately encrypt-on-send rather than block-on-send by default - see the entry's own summary for why.
- `gdpr-uk-government-id-and-special-category` - GDPR/UK GDPR, UK-specific national identifiers + EU passport + Art. 9 special-category (health) logic. Deliberately scoped narrow (UK types + generic EU passport, not all 27 member states' formats) - see its caveats.
- `credentials-and-secrets-leak-prevention` - cross-regulation (all three), a generic security-safeguard control rather than an identity/health one.
- `financial-banking-data` - POPIA/GDPR, general safeguards (not special-category) citation. Flags a real gap: no South-Africa-specific bank-account SIT exists, so this is weaker on domestic SA banking data than international wire details.
- `payment-card-data` - POPIA/GDPR, explicitly **not** a PCI DSS compliance claim (PCI DSS is out of v1 scope). Volume-tiered rule logic (1-9 instances warn, 10+ block+alert), the one entry that departs from the single-trigger shape.
- `bulk-pii-exfiltration` - POPIA/GDPR, reuses existing SITs at a 50+ instance threshold rather than introducing new ones; depends on `financial-banking-data`'s SITs, built after it.
- `ip-contracts-source-code` - **no regulation** (POPIA/GDPR/HIPAA don't govern IP), **E5-only, no Business Premium/E3 fallback** (2026-09-22 decision - a keyword-based approximation was deliberately not shipped). Uses Trainable Classifiers, not Sensitive Information Types. Its PowerShell template deliberately stops at the policy shell and defers the classifier-based rule condition to the portal UI, since the real cmdlet parameter for that wasn't reliably known - the one entry where the script is incomplete on purpose rather than merely unverified.

In-depth planning for the last four: [[DLP Stage 3 - Remaining Data Categories]]. PCI DSS itself is deliberately out of v1 scope despite Crimson Line Live Demo already having a live PCI DSS DLP policy (in simulation mode) - see the plan.

**9th entry, `popia-cross-border-transfer` (added after user review, 2026-09-22):** the user asked directly whether POPIA coverage was really just the SA ID/health entry - answer: no, POPIA already tagged 5 of 8 entries at that point (identity+health, banking, cards, bulk exfiltration, credentials). Reviewing what was genuinely still missing surfaced one real gap: every existing entry checks "recipient is outside my organization," a generic condition, not POPIA s.72's actual rule (personal information may not leave South Africa without adequate protection). This entry is the first destination-based control in the catalog rather than a content-type one - it introduced a new `DataCategory` value, `cross_border_transfer`, since it doesn't fit any of the seven content-type categories (it's about where data goes, not what it is). Mechanism: a Sensitive Information Type condition (South Africa Identification Number) combined with a `-ExceptIfRecipientDomainIs` exception against a client-maintained approved-domains list - Exchange-only, since the domain-exception mechanism doesn't apply to SharePoint/OneDrive external sharing (that needs the SharePoint admin center's own allowed-domains setting instead, called out explicitly in the entry's caveats rather than papered over).

Two categories were deliberately **not** turned into entries, for the same reason `ip_contracts` shipped E5-only: POPIA's other "special personal information" categories (race/ethnic origin, religious/political belief, trade union membership, sex life, biometric data, criminal behaviour - s.26) and children's personal information (s.34-35, relevant given the fleet includes a school tenant) have no reliable built-in Sensitive Information Type - only a weak keyword/classifier approximation is possible below E5, which would be the least effective entry in the catalog. Recorded as a known, documented gap rather than shipped weakly.

## `relatedRecommendationIds` - cross-linking overlapping entries (2026-09-22)
The user pushed back on the 9th entry directly: doesn't this duplicate the first POPIA entry, since both key on "South Africa Identification Number"? They don't - one restricts *who* data is shared with (POPIA s.19/26/32), the other restricts *where* it ends up (POPIA s.72), and the two even use genuinely different mechanisms (a generic external-recipient condition vs. a domain-allowlist exception, the latter Exchange-only) - merging them would have required either an inaccurate `recommendedLocations` claim or a data-model change for per-rule locations. But the underlying concern (does this look like accidental duplicate content) was legitimate, so a new optional `DlpRecommendation.relatedRecommendationIds?: string[]` field was added instead of merging: a reciprocal link between the two entries, rendered as a "Related recommendations - overlapping topic, different question" card immediately under the header (not buried in caveats), with a clickable row per related id that jumps to it (`handleSelectRelated`, scrolls to top so the jump is visible). Reusable for any future entry pair that overlaps this way - keep it reciprocal (if A lists B, B should list A) when adding new entries.

Part of the same session's decision-tree: separate-with-explicit-linking was chosen over merge-and-caveat, matching the module's established preference for surfacing distinctions explicitly rather than collapsing them for a shorter list.

## Styling correction (2026-09-22)
Shipped first with an ad hoc look (rounded-lg cards, indigo accents, dark-mode-only hardcoded colors, no page-level padding wrapper) that didn't match the rest of the app and had no light-mode support at all - a real bug, not just a preference mismatch, since the app supports a light/dark toggle everywhere else. Rebuilt to mirror `SecureScoreModule.tsx`/`MfaAuditModule.tsx`'s actual house pattern: `p-5 max-w-[1600px] mx-auto` page wrapper, a bordered `bg-[#F8FAFC] dark:bg-slate-900/50` header bar, `rounded-sm` cards (not `rounded-lg`) with `border-[#CBD5E1] dark:border-slate-700` and `shadow-xs`, uppercase `text-xs font-bold` section headers with a `border-b` divider, and every color given both a light and dark pairing. Worth checking any future module built in this codebase against these two existing modules' actual source before assuming a self-consistent design is enough - "looks fine on its own" and "matches the app" are different bars, and light-mode support specifically is easy to silently skip since this app (and most dev sessions) tend to run in dark mode by default.

## Sensitivity labels shipped (2026-09-22)
The module's own name promised "DLP & Sensitivity Labels" since it was first built, but every entry until now was a DLP rule - a real gap the user caught directly. Closed the same day, per explicit direction ("make it a category under the DLP" - i.e. one catalog, one module, a visible category distinction, not a separate module or list):

- New `LabelRecommendation` type in `data-protection-recommendations.ts`, structurally different from `DlpRecommendation` (a taxonomy + a label policy + optionally an auto-labeling policy, not a single SIT-based rule) - see [[Sensitivity Labels Catalog Plan]] for why a separate type was necessary, the same reasoning that kept the two POPIA entries from being merged.
- `DATA_PROTECTION_RECOMMENDATIONS` is now `DataProtectionCatalogEntry[]` (`DlpRecommendation | LabelRecommendation`), discriminated by `"kind" in entry && entry.kind === "label"` - DLP entries carry no `kind` field at all (existing 9 entries untouched, no edits needed to them). `DataProtectionModule.tsx` uses a real TypeScript type predicate (`isLabelEntry`), not a plain boolean, so the union narrows correctly in each render branch.
- Four label entries: a baseline four-tier taxonomy (Public/General/Confidential/Highly Confidential, mandatory labeling, no regulation-specific fallback needed since a documented taxonomy is cited by all three regs' general safeguards provisions), Highly Confidential encryption, E5-only auto-labeling for PHI/SA ID/government ID content (reusing the exact SITs the matching DLP entries already define, cross-linked both directions via `relatedRecommendationIds`), and container labels for Teams/sites/groups.
- `New-Label`/`New-LabelPolicy`/`New-AutoSensitivityLabelPolicy` are well-documented public cmdlets, verified against Microsoft Learn during planning - materially higher PowerShell confidence than the earlier `ip_contracts` trainable-classifier gap. The mandatory-labeling/downgrade-justification `-AdvancedSettings` keys and the encryption/container-label parameter shapes are less commonly documented and flagged accordingly in each entry's own caveats.
- `ip_contracts`' E5-only-no-fallback precedent was re-applied to the auto-labeling entry, for the same reason: a fake imitation of automation below E5 would be worse than no entry.
- `compliance-evaluator.ts`'s existing "DLP recommendations available" control (POPIA/GDPR/HIPAA Readiness, item 1.4) deliberately still excludes label entries, so its own name keeps meaning what it already said before labels joined the same array - the QBR's `dataProtectionSection` deliberately does the opposite (counts both), since its own heading already said "DLP & Sensitivity Labels."
- `query_data_protection_recommendations` (MCP tool) now returns a `kind` field per entry and branches its full-detail response between DLP and label fields.
- Sidebar/list UI: a small "DLP" vs "Label" badge on every card (slate vs indigo), plus a new "DLP & Labels / DLP only / Sensitivity labels only" filter dropdown alongside the existing regulation/data-category ones.

## Sequence vs. relatedness fix (2026-09-22)
Direct user feedback: the four label entries looked like interchangeable alternatives, not a foundation plus three optional layers on it. Root cause found on inspection: the "Related recommendations - overlapping topic, different question" card (built for the two POPIA entries, which genuinely are two separate questions) had been reused for the label entries' relationships too - but those are a **different kind of relationship entirely** (a real build order), and reusing the same card with the same "different question" framing actively implied the wrong thing.

Fixed structurally, not just with better wording:
- New `LabelRecommendation.recommendedFor: string` (required) - explicit, concrete guidance on which clients/scenarios each entry fits, rendered prominently right under the summary, not buried in prose.
- New `LabelRecommendation.buildsOn?: string[]` - the real "you need that deployed first" relationship, kept structurally separate from `relatedRecommendationIds`. Rendered as its own amber-styled "Deployment sequence" card, visually distinct from the neutral "Related recommendations" card, so the two relationship types can never blur together again.
- The forward direction ("what can I add once this is deployed") is **computed**, not stored - `extendedByIds()` scans the catalog for entries whose `buildsOn` references the current one. Each entry only declares its own backward dependency once; the forward view can never drift out of sync the way a hand-maintained reciprocal field could.
- Corrected the three sequence links that had been wrongly stored in `relatedRecommendationIds` when the four label entries first shipped (an honest mistake, not caught until this feedback) - `relatedRecommendationIds` on the label entries now carries only genuine different-question links (the auto-labeling entry's three matching DLP entries).
- Verified live: the baseline taxonomy entry now shows "Recommended for: every client... this is the ROOT" plus a sequence card listing both things that build on it; the encryption entry shows both directions at once (deploy the taxonomy first, then optionally add auto-labeling).
